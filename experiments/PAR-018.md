# PAR-018 Attribute 색상 분류 n=5 Dataset의 과최적화된 수치를 n=21로 재검증하고, 근거 없는 무채색 확신도 기능 추가를 보류함

관련 실험: EXP-025(Attribute Metadata 색상 분류 Baseline/A/B, PAR-016), EXP-026(FC-012 재검토,
Gray World WB, PAR-017), EXP-027(coco128 기반 n 확장 재검증 + 무채색 신호 분리도 분석)

## 1. 한줄 요약
Attribute 색상 분류 Accuracy가 n=5(zidane.jpg/bus.jpg crop)에서 측정한 32~48%였던 것을
coco128 실제 인물 crop 21개로 재검증하니 15~32%로 절반 가까이 떨어짐을 확인했고, Roadmap이
다음 단계로 제안했던 "무채색 확신도 기반 unknown fallback"도 후보 신호(채도, raw BGR 표준편차)
둘 다 achromatic/chromatic을 분리하지 못함을 실측으로 확인해 설계·구현을 보류했다.

## 2. 문제가 뭐였는가?
EXP-025/026에서 Attribute 색상 분류(Baseline/A/B/B_wb)의 성능을 ultralytics 패키지에 번들된
이미지 2장(zidane.jpg, bus.jpg)에서 나온 person crop **5개**만으로 측정했다. 이 5개 중 4개가
GT upper=black이어서 검정 옷에 심하게 편중됐고, Roadmap 01. Architecture & Roadmap에는 이
한계가 "n=5 작은 Dataset·낮은 색상 다양성"으로 명시적으로 남아 있었다. 동시에 FC-012(검정
옷의 조명 오분류)의 다음 대안으로 "무채색 확신도 점수 기반 unknown 표시"가 제안됐지만, 이
신호가 실제로 achromatic과 chromatic을 구분할 수 있는지는 한 번도 검증되지 않았다.

## 3. 왜 이 문제가 중요했는가?
Attribute Metadata(상/하의 색상)는 카지노 VMS 검색에서 "녹색 재킷을 입은 사람" 같은 질의를
가능하게 하는 핵심 Metadata다(지침 19). 그러나 n=5로 측정한 낙관적인 수치(40~48%)를 그대로
믿고 MetadataStore/VMS API에 연결했다면, 실제 다양한 인물·조명·배경을 가진 카지노 CCTV
환경에서는 훨씬 낮은 Accuracy(15~32%)로 운영되며 검색 결과에 신뢰할 수 없는 Attribute가
대량으로 섞이는 결과를 낳았을 것이다 — 이는 단일 기능 버그가 아니라 **"작은 Dataset의 지표를
믿고 다음 단계(API 연결)로 넘어갈 뻔한" 방법론적 위험**이었다. 또한 검증 없이 "무채색 확신도"
기능을 설계부터 시작했다면, 분리되지 않는 신호 위에 임계값만 조정하며 시간을 소모했을 것이다
— 지침 55("가설이 반대라도 그대로 기록")와 지침 38(실패를 숨기지 않는다)이 요구하는 바로 그
상황이다.

## 4. 원인이 뭐였는가?
`results/EXP-027/predictions.csv`와 `achromatic_signal.csv`에 근거한다.
- **Accuracy 하락의 원인**: coco128 crop은 zidane.jpg/bus.jpg보다 배경이 풍부한 실제 스냅샷이라
  bbox 평균(Baseline) 또는 단순 분할 평균(A)이 배경/가구/잔디 색으로 더 쉽게 끌려갔다. 실측
  예: `000000000086_0`(검정 자켓)의 Baseline 예측이 upper=gray, `000000000165_1`(검정 정장)은
  upper=orange로 나옴 — 피부·배경·조명이 섞인 평균이 실제 옷 색과 무관하게 수렴.
- **무채색 신호 분리 실패의 원인**: HSV 채도 S는 achromatic 영역 평균 64.46 vs chromatic 영역
  평균 121.29로 차이가 있어 보이지만, achromatic 최댓값(158.89, `000000000572_0`의 어두운
  니트)이 chromatic 최솟값(62.92, `000000000623_0`의 분홍 바지)보다 훨씬 높아 완전히 겹친다.
  raw BGR 채널 표준편차는 아예 평균이 거의 같다(achromatic 55.26 vs chromatic 56.54). 두
  신호 모두 "영역 내 옷 색 하나"가 아니라 배경 Bleed·하이라이트/그림자·JPEG 압축 Noise가 섞인
  실제 픽셀 분포를 반영하기 때문으로 분석된다 — `region_dominant_color()`가 S/V 극단값과
  피부색을 걸러내려 시도해도(EXP-025), 필터를 통과한 "대표 영역" 자체가 색상군 간에 깔끔히
  갈리지 않는다.

## 5. A를 고민하였는데 왜 안 했는가?
**A: n=5 측정값(32~48%)을 그대로 신뢰하고, Roadmap이 제안한 무채색 확신도 fallback을 바로
설계·구현한다.** 장점은 빠르다는 것(이미 방향이 정해져 있었음)과, EXP-026에서 어느 정도
분석적 근거(채도가 조명 Cast에 부풀려진다는 가설)가 이미 있었다는 점이다. 하지만 n=5는
통계적으로 method 간 우열조차 신뢰하기 어려운 표본이며(5개 중 4개가 동일 GT 색상), 검증
없이 "확신도 임계값"을 설계하면 분리되지 않는 신호 위에서 임의의 threshold를 고르는 것과
같아 재현성이 없다. 지침 31("정확하게 측정할 수 없는 Metric은 억지로 작성하지 않는다")과
"처음부터 완성된 코드를 제공하여 문제를 없애버리지 않는다" 원칙에 반하므로 선택하지 않았다.

## 6. B를 고민하였고 왜 적용했는가?
**B: coco128(실제 COCO 128장)에서 person crop을 추가로 모아 n을 21로 늘려 재측정하고, 무채색
신호(S, raw BGR std)의 실제 분리도를 먼저 정량적으로 확인한 뒤에 fallback 설계 여부를
결정한다(채택).** egress 제약으로 Wikimedia 등 원본 영상은 이번에도 접근 불가했지만, coco128
은 `ultralytics`의 공식 `coco128.yaml`에 명시된 GitHub Release Asset 경로
(`v0.0.0/coco128.zip`, 이전 세션이 틀리게 시도했던 `v8.3.0` 태그가 아님)로 정상 다운로드됨을
새로 확인해 실행 가능했다. 실제 측정 결과 두 후보 신호 모두 분리되지 않음을 확인했으므로, B를
택한 덕분에 "검증 안 된 기능을 설계부터 시작"하는 비용을 피할 수 있었다 — 측정이 설계보다
먼저여야 한다는 이 프로젝트의 핵심 원칙(Baseline → 실제 테스트 → 측정 → 분석 → 비교 → 선택)
그대로다.

## 7. 어떤 방식으로 검증했는가?
- **Dataset**: coco128 128장 전체에서 YOLO11n(conf=0.4, person class, bbox>=120x250px)으로
  검출한 crop 45개 중, 상/하의가 모두 보이고 단일 색으로 판단 가능한 21개를 Read 도구로
  직접 확대해 보며 수동 Ground Truth 라벨링(지침 31).
- **환경/Configuration**: `.venv` 신규 생성(Python 3.11, CPU 전용), `src/attributes/color.py`
  의 기존 4가지 method(baseline/a/b/b_wb) 파라미터 변경 없음. EXP-025와 동일한 5가지 합성
  조명(normal/low_light/strong_light/warm_cast/cool_cast)을 동일 Config로 재적용.
- **Metric**: method x 조명 조건 x GT 21개(상/하 210셀/method)의 Overall/조건별 Accuracy,
  GT=black 셀만 슬라이싱한 Accuracy(EXP-026과 동일 패턴), achromatic vs chromatic 영역의
  채도/raw BGR 표준편차 분포(평균/90·10퍼센타일/최댓·최솟값, 겹침 여부).
- **Baseline 비교**: EXP-025/026의 n=5 수치(Baseline 32%, A 28%, B 40%, B_wb 48%)와 동일
  정의로 비교.
- **Regression Test**: `src/attributes/color.py`는 변경하지 않았으므로(측정만 수행) 기존
  `tests/test_attribute_color.py`는 그대로 통과함을 재확인했다 — 아래 8번 Test Suite 결과 참고.

## 8. 개선된 수치적인 결과가 무엇이었는가?

Attribute Accuracy (n=5 → n=21, 전체 조명 평균):

| Metric | n=5 (EXP-025/026) | n=21 (EXP-027) |
|---|---|---|
| Baseline Overall Accuracy | 32% | 15.2% |
| 대안 A Overall Accuracy | 28% | 15.7% |
| 방법 B(production) Overall Accuracy | 40% | 26.2% (normal 조명만: 33.3%) |
| B_wb(실험용) Overall Accuracy | 48% | 32.4% (normal 조명만: 35.7%) |
| GT=black Accuracy (방법 B) | 측정 안 함(n=5 전용 지표 없음) | 39.1% (43/110) |

무채색 신호 분리도(신규 측정, Before 없음 — 이번이 최초 검증):

| 신호 | achromatic 평균/최댓값 | chromatic 평균/최솟값 | 분리됨? |
|---|---|---|---|
| HSV 채도 S | 64.46 / 158.89 | 121.29 / 62.92 | 아니오 (완전히 겹침) |
| raw BGR 채널 표준편차 | 55.26 / 89.92 | 56.54 / 36.74 | 아니오 (평균 거의 동일) |

이번 변경은 "개선"이 아니라 "재측정을 통한 눈높이 보정"이다 — method 순위(baseline≈A < B <
B_wb)는 n=21에서도 유지되어 EXP-025/026의 상대적 결론은 재확인됐지만, 절대 Accuracy는
이전 기록보다 정직하게 낮춰 다시 기록했다. 이는 "성과를 위해 숫자를 조작하거나 실패 결과를
숨기지 않는다"(지침 38)는 원칙에 따른 의도된 결과다. 신규 pytest 6개 추가(coco128 GT
라벨/achromatic 신호 분석 로직), 전체 suite 191 passed / 7 skipped(기존 skip 유지, 회귀 없음).

## 9. 재발 방지 대책
- **작은 n(<10)으로 측정한 Accuracy를 README/Notion에 "운영 가능한 성능"으로 재인용하지
  않는다** — 이번 experiment.md Decision에 n=5 수치는 "작은 Dataset에서의 상대 비교 전용"
  이라고 명시했다.
- **제안된 기능(무채색 확신도 fallback)을 설계하기 전에, 그 기능이 의존하는 신호의 분리도부터
  먼저 수치로 검증하는 순서를 지킨다** — 이번 실험의 `achromatic_signal.csv`/`summary.json`이
  그 검증 결과를 영구 기록으로 남겨, 같은 아이디어가 재차 제안되더라도 이 데이터를 먼저
  참고하도록 한다.
- Regression Test: `tests/test_attribute_color.py`에 coco128 기반 GT 분석 로직(achromatic
  신호 계산)에 대한 단위 테스트를 추가해, 향후 `split_upper_lower()`/`_to_hsv()` 등 내부
  함수가 바뀌어도 이번 측정이 사용한 신호 계산 방식이 깨지면 즉시 드러나도록 했다.
- `results/EXP-027/`의 crops/predictions.csv/achromatic_signal.csv/summary.json을 보존해,
  다음 세션이 더 큰 n(원본 영상 접근 복구 후)으로 재검증할 때 Before 비교 기준으로 쓸 수
  있게 했다.
