# PAR-005 Line Crossing 왕복 중복 이벤트(FC-007) — 선 양쪽 불감대(Hysteresis)로 제거

관련 실험: EXP-006, EXP-012, EXP-014

## 1. 한줄 요약
선 근처에서 검출 박스가 몇 픽셀만 흔들려도 Line Crossing이 반복 발생하는 문제(FC-007)를
900프레임 재현 실험(57건 중 24건 중복 반전)으로 확인하고, 선까지의 거리가 band_px 이상일
때만 확정 side를 바꾸는 Hysteresis를 적용해 같은 조건에서 중복을 0건으로 제거했다.

## 2. 문제가 뭐였는가?
`LineCrossingDetector`는 가상선을 기준으로 한 쪽(side)이 바뀌는 순간마다 무조건
Crossing 이벤트를 냈다. 사람이 선 근처에 멈춰 있거나 Detection bbox가 프레임마다
몇 픽셀 흔들리기만 해도 side가 반복적으로 뒤집혀, 실제로는 한 번 지나간 것을
A_TO_B/B_TO_A가 번갈아 여러 번 기록하는 왕복 중복 이벤트가 발생했다(Notion 05. Failure
Cases FC-007: 실내 장면에서 76건 중 26쌍이 0.6초 이내 방향 반전으로 관찰됨). 이번
세션에서 동일한 성격의 문제를 이 저장소의 `LineCrossingDetector`에 대해 직접 재현
실험으로 확인했다(band_px=0 기준 57건 중 24쌍 중복, EXP-014).

## 3. 왜 이 문제가 중요했는가?
Line Crossing은 카지노 CCTV에서 출입 동선 추적(Entrance→Casino Floor)과 People
Counting(EXP-012)의 기초 이벤트다. 왕복 중복 이벤트는 VMS Search에서 "이 사람이 선을
몇 번 통과했는가"를 조회할 때 실제 통행량을 몇 배로 부풀리고, People Counting의
IN/OUT 순증감 계산을 왜곡한다(EXP-012가 이미 이 영향을 받아 자체적으로 band를
도입했음). 또한 Metadata Pipeline에 저장되는 Event 이력 자체가 노이즈로 오염되면
사후 포렌식 검색(카지노 부정행위 조사 등)에서 "언제 실제로 이동했는지"를 신뢰할 수
없게 되는 연쇄 영향이 있다.

## 4. 원인이 뭐였는가?
`src/events/line_crossing.py`의 `side_of_line()`을 코드로 직접 확인한 결과, 선을
기준으로 한 쪽을 구분하는 dead zone이 부동소수점 오차 수준(1e-6)뿐이었다. 실측으로
확인하기 위해 EXP-014에서 ultralytics 내장 실제 사진(bus.jpg)에 EXP-010과 동일한
Pan Jitter를 준 900프레임을 YOLO11n+ByteTrack으로 실제 추론하고, 관측된 bottom-center
y좌표의 중앙값을 지나는 가상선을 배치해 재생했다. band_px=0(기존 동작)에서 총 57건의
이벤트 중 24쌍이 같은 Track에서 0.6초 이내에 방향이 반대로 뒤집히는 패턴으로
나타났다 — Detection bbox의 정상적인 프레임 간 흔들림만으로도 로직상 반드시
발생하는 구조적 문제임을 코드와 실측 양쪽에서 확인했다.

## 5. A를 고민하였는데 왜 안 했는가?
Track별로 이벤트 발생 후 일정 프레임(Cooldown, 이번 실험에서는 0.6초=15프레임) 동안
같은 Track의 새 이벤트를 무시하는 시간 기반 Debounce를 검토했다. EXP-014에서 실제로
구현해 같은 900프레임에 대해 측정한 결과 33건/중복 0건으로 Hysteresis(31건/중복 0건)와
거의 동등한 억제 효과를 보였다. 그럼에도 채택하지 않은 이유는 (1) Cooldown 프레임 수가
FPS에 의존적이라 카메라/코덱마다 다른 실제 CCTV 환경에서 재조정이 필요하고 처리 FPS가
변하면(Edge Camera의 프레임 드랍 등) 같은 프레임 수가 더 이상 같은 시간을 의미하지
않으며, (2) "최근에 이벤트가 있었으니 억제한다"는 것은 왜 억제되는지에 대한 기하학적
근거가 없어 실제로 빠르게 왕복한 사람의 두 번째 이벤트까지 구분 없이 묻어버릴 수 있기
때문이다.

## 6. B를 고민하였고 왜 적용했는가?
선까지의 부호 있는 거리 `|d| >= band_px`일 때만 확정 side를 바꾸는 Hysteresis(Schmitt
Trigger)를 적용했다. A와 달리 "선에서 실제로 몇 픽셀 떨어져 있는가"라는 기하학적
의미가 있어 카메라 설치 위치/해상도에 맞춰 튜닝할 근거가 명확하고, FPS 변화에 영향받지
않는다. 또한 같은 저장소의 People Counting(EXP-012)이 이미 동일한 설계(선까지의 거리
기반 불감대)를 쓰고 있어, "선 관련 판정은 band_px 불감대로 처리한다"는 일관된 패턴을
코드베이스 안에서 유지할 수 있다는 점도 채택 이유다.

## 7. 어떤 방식으로 검증했는가?
- **Dataset**: 이 원격 세션은 egress 정책상 Wikimedia 접근이 여전히 차단되어(EXP-010과
  동일 제약, curl로 403 재확인) ultralytics 내장 실제 사진(bus.jpg)에 EXP-010과 동일한
  Pan Jitter 파라미터를 적용해 900프레임을 생성했다.
- **환경/Configuration**: YOLO11n(conf=0.4, imgsz=640) + ByteTrack, `band_px in {0,3,5,10,20}`
  sweep과 Cooldown(15프레임) 변형을 **동일한 캐싱된 bbox 시퀀스**에 대해 재생해 궤적
  차이가 아닌 로직 차이만 비교되도록 했다(EXP-014 Configuration 참고).
- **Metric**: 총 이벤트 수, 같은 Track에서 방향이 반대인 이벤트가 0.6초 이내에 연속
  발생하는 "중복 반전 쌍" 수(Notion에 이미 기록된 FC-007 관찰 기준과 동일 정의 사용).
- **Baseline**: band_px=0 (기존 코드 동작 그대로).
- **Regression Test**: 기존 `tests/test_line_crossing.py` 7개를 수정 없이 그대로
  통과시켜 하위 호환을 확인했고(band_px 기본값 0), FC-007 재현/억제/진짜 통과 감지를
  검증하는 신규 테스트 5개를 추가했다. 전체 `pytest tests/ -q` 53 passed, 7 skipped로
  다른 모듈에 회귀가 없음을 확인했다.

## 8. 개선된 수치적인 결과가 무엇이었는가?

| Metric | Before (band_px=0) | After (band_px=5) |
|---|---|---|
| 총 Line Crossing 이벤트 (900프레임) | 57 | 31 |
| 0.6초 이내 방향 반전(중복) 쌍 | 24 | **0** |
| Unit Test | 7개(기존) | 12개(신규 5개 추가, 0 실패) |
| 전체 회귀 테스트 | 48 passed | 53 passed |

비교 대안(Cooldown, 미채택): 총 33건 / 중복 0건 — Hysteresis와 억제 효과는 비슷했으나
위 5번 이유로 채택하지 않음.

## 9. 재발 방지 대책
- `tests/test_line_crossing.py`에 FC-007 재현 테스트(`band_px=0`에서 흔들림이 실제로
  반복 이벤트를 만든다는 것을 보이는 회귀 테스트)를 남겨, 향후 누군가 `side_of_line`의
  dead zone 로직을 실수로 건드려도 즉시 실패하도록 했다.
- `scripts/run_full_pipeline.py`(실제 통합 파이프라인)에 `LINE_CROSSING_BAND_PX = 5`
  상수와 주석(FC-007/EXP-014/PAR-005 참조)을 남겨, 이 값이 임의의 매직 넘버가 아니라
  실험에서 도출된 값임을 코드에서 바로 추적할 수 있게 했다.
- band_px=5는 GT 없이 정성/정량 혼합으로 결정한 임시값임을 experiment.md에 명시하고,
  MOT20-01 GT 확보 후 band별 MAE 재측정을 Next Action으로 남겼다(EXP-012와 동일한
  한계 공유 — 두 모듈이 같은 재검증을 필요로 한다는 것도 문서화해 두었다).
- 새 상태 판정 로직(현재는 ROI/Loitering/Line Crossing/People Counting)에 dead
  zone/hysteresis가 필요한지 여부를 08. Technical Decisions에 "선/영역 경계 판정
  원칙"으로 기록해, 다음에 유사한 경계 판정 로직을 새로 만들 때 처음부터 흔들림을
  고려하도록 한다.
