# PAR-011 Adaptive Recording Circular Buffer 도입과 버퍼 용량 Off-by-One 발견/수정

관련 실험: EXP-019, EXP-020

## 1. 한줄 요약
Event Clip Hybrid 생성이 IDLE 겹침 구간을 결정론적으로 "재생성"하던 편법을 실제
Circular Buffer로 대체하는 과정에서, 버퍼 용량을 Pre-Roll 프레임 수와 똑같이 설정하면
트리거 프레임 자신을 놓쳐 정확히 1프레임이 항상 누락되는 Off-by-One을 발견하고,
`pre_roll_frames+1` 이상으로 용량을 계산하는 헬퍼와 완전성 사전 점검으로 수정해
동일 시나리오에서 Clip 누락을 0으로 만들었다.

## 2. 문제가 뭐였는가?
EXP-019(PAR-010)에서 채택한 Hybrid Event Clip 생성 방식은 Active Stream에 없는(=IDLE
Tier) Pre-Roll 구간을 `make_frame()`이라는 결정론적 합성 함수로 다시 만들어 메웠다.
이 방식은 실험 시나리오에서만 가능한 편법이고, 실제 카메라는 이미 지나간 원본 프레임을
재생성할 수 없다는 한계가 EXP-019 Next Action으로 명시적으로 남아 있었다. 이번 PAR은
지침 23이 요구하는 실제 Circular Buffer를 구현하고 실험한 기록이다. 구현 과정에서
버퍼 용량을 "Pre-Roll 초수 × FPS"(가장 직관적인 계산, 250프레임)로 설정했더니, Event가
트리거된 순간에도 정확히 1개 프레임(가장 오래된 Pre-Roll 시작 프레임)이 이미 버퍼에서
밀려나 있어 Clip이 항상 1프레임 모자란 채로 만들어지는 것을 실측으로 발견했다.

## 3. 왜 이 문제가 중요했는가?
Circular Buffer는 카지노 CCTV에서 "사고 직전 몇 초"를 실제로 복구할 수 있는 유일한
장치다 — 이게 없으면 EXP-019/PAR-010이 지적한 대로 Pre-Roll이 IDLE 구간까지 파고들 때
Event Clip이 조용히 불완전해진다(FC-008과 같은 클래스의 문제). 그런데 이 버퍼 자체의
용량을 잘못 계산하면, "Circular Buffer를 도입했으니 문제가 해결됐다"는 착각 속에서
매번 정확히 1프레임씩 누락되는 새로운 조용한 버그를 만들 수 있다. Off-by-One은 코드
리뷰나 육안 검토로는 거의 드러나지 않는 종류의 버그이고(1프레임=0.04초 차이는 영상을
재생해봐도 알아채기 어렵다), 보안 Event Clip처럼 "완전성"이 핵심 요구사항인 산출물에서는
이런 미세한 결함이 누적되면 포렌식 신뢰도 자체를 훼손한다. Edge Camera(버퍼 유지)와
NVR/VMS(Clip 추출) 양쪽에 걸친 설계 문제이기도 하다.

## 4. 원인이 뭐였는가?
`src/recording/circular_buffer.py`의 `FrameCircularBuffer.push()`를 직접 분석한 결과,
버퍼는 capacity_frames를 초과하는 즉시 가장 오래된 프레임을 evict한다. Event가 프레임
`t`에서 트리거되면, 버퍼는 이미 프레임 `t`까지 push된 상태이므로 이 시점에 버퍼가 들고
있는 가장 오래된 프레임은 `t - capacity + 1`이다. Pre-Roll이 요구하는 시작 프레임은
`t - pre_roll_frames`인데, `capacity == pre_roll_frames`로 설정하면
`t - capacity + 1 == t - pre_roll_frames + 1`이 되어 정확히 `t - pre_roll_frames`
프레임(요청 구간의 맨 앞)이 이미 사라진 뒤다. EXP-020에서 실제로
`buf.coverage(1089, 1200)`를 호출해 `missing_frames == (1089,)`로 정확히 1개만 빠진
것을 확인해, 추측이 아니라 코드와 실측값 양쪽으로 원인을 검증했다.

## 5. A를 고민하였는데 왜 안 했는가?
**A: 버퍼 용량을 넉넉하게(예: 전체 스트림 길이만큼, 또는 매우 큰 고정값으로) 잡아
"충분히 크면 문제없다"는 방식으로 회피한다.** 실측으로 EXP-020에서 확인했듯 원본 BGR
프레임은 810×1080 기준 1프레임당 2.5MB이며, capacity를 301(약 12초 분량)만 잡아도
채널당 753MB가 필요하다. 카지노처럼 채널이 수백 개인 환경(CLAUDE.md 지침 8)에서
"넉넉하게"를 기준으로 삼으면 메모리 요구량이 채널 수에 선형으로 폭증해 PAR-004(BestShot
무제한 누적 Memory Leak)와 같은 클래스의 문제를 버퍼 설계 단계에서 다시 만들게 된다.
근본 원인(Off-by-One 계산 오류)을 고치지 않고 용량만 키우는 것은 문제를 가리는 것이지
고치는 것이 아니라고 판단해 채택하지 않았다.

## 6. B를 고민하였고 왜 적용했는가?
**B: 필요한 최소 용량을 수식으로 정확히 계산하는 헬퍼(`required_capacity_for_pre_roll`
= `pre_roll_frames + 1 + safety_margin_frames`)를 만들고, Clip을 조립하기 전 반드시
`coverage()`로 완전성을 확인해 불충분하면 예외를 던지도록 강제**하는 방식을 채택했다.
이 방식은 (1) Off-by-One의 근본 원인(트리거 프레임 자신도 버퍼에 남아있어야 한다는 점)을
수식 자체에 명시해 재발을 막고, (2) 메모리 비용을 실제 필요량(Pre-Roll 길이)에 정확히
비례하게 유지해 A처럼 채널 수에 비례해 폭증하지 않으며, (3) 설정이 여전히 부족한 경우
(Edge Camera 메모리 예산 제약 등)에도 조용히 틀린 결과를 내지 않고 `KeyError`로 명시적
실패를 강제한다는 점에서 EXP-019/FC-008에서 이미 검증한 "완전성 사전 점검" 원칙과
일관된다. EXP-020에서 이 방식으로 capacity=251(exact_minimum)부터 실제로 완전한 Clip이
만들어지고, capacity=301(production 마진 포함)까지 동일하게 완전함을 실측으로 확인했다.

## 7. 어떤 방식으로 검증했는가?
EXP-019와 동일한 1,600프레임(IDLE 75%, Pre-Roll이 IDLE Tier까지 파고드는 경계 사례)
시나리오를 그대로 재사용했다. Detection/Tracking/ROI 결과는 EXP-019가 실제
YOLO11n+ByteTrack으로 추론해 캐시한 `results/EXP-019/detection_cache.json`을 재사용해
(같은 로직을 다시 추론하는 낭비를 피함), Recording/Circular Buffer 계층만 바꿔 측정했다.
4가지 용량 시나리오(64/250/251/301프레임)로 각각 프레임을 실제로 push하고,
`coverage()`/`get_range()`로 완전성을 확인한 뒤 완전한 경우에는 실제 FFmpeg(libx264)로
IDLE 구간을 인코딩하고 Active Stream Stream Copy 결과와 concat해 최종 Clip 파일을
만들어 ffprobe(rawvideo 디코딩 기반, EXP-019와 동일 방식)로 실제 프레임 수를 검증했다.
`tests/test_circular_buffer.py`에 12개 Unit Test(용량 초과 eviction, coverage 완전/불완전,
get_range의 예외 전파, Off-by-One 재현 테스트 2개 포함)를 추가했고, 전체 `pytest tests/`
117 passed/7 skipped로 Regression Test를 완료했다(기존 105개는 무수정으로 통과).

## 8. 개선된 수치적인 결과가 무엇이었는가?

| Capacity 설정 | Capacity(프레임) | 메모리 | Coverage | Clip 결과 |
|---|---|---|---|---|
| Edge 예산 과소 설정 | 64 | 160.18 MB | 불완전 (112프레임 누락) | 명시적 실패(KeyError), Clip 미생성 |
| Off-by-One (=pre_roll_frames) | 250 | 625.71 MB | **불완전 (정확히 1프레임 누락)** | 명시적 실패(KeyError), Clip 미생성 |
| 정확한 최소값 (+1) | 251 | 628.21 MB | **완전** | 511/511 프레임, 파일 크기 EXP-019 Hybrid와 완전 동일(5,763,825 bytes) |
| 운영 권장값 (+2초 마진) | 301 | 753.35 MB | **완전** | 511/511 프레임, 동일 결과 |

정성적 결과: capacity=250에서 발생하는 Off-by-One은 이번 실험 전까지는 "Circular Buffer만
있으면 해결된다"는 막연한 가정 뒤에 숨어 있었으나, 실제 구현·측정을 통해 "얼마나
잘못됐는지"(정확히 1프레임)까지 구체적으로 드러냈다.

## 9. 재발 방지 대책
- `required_capacity_for_pre_roll()`을 Off-by-One을 코드 리뷰가 아니라 수식으로 방지하는
  단일 진입점으로 두어, 앞으로 버퍼 용량을 손으로 계산해 다시 같은 실수를 반복하지
  않도록 했다.
- `tests/test_circular_buffer.py`에 `test_capacity_exactly_pre_roll_frames_misses_trigger_frame_itself`와
  `test_capacity_with_required_helper_covers_trigger_frame_exactly`를 고정해, 향후 버퍼나
  용량 계산 로직이 바뀌어도 이 Off-by-One이 회귀하면 즉시 실패하도록 했다.
- `get_range()`는 하나라도 누락되면 무조건 예외를 던지도록 설계해(부분 반환 금지), FC-008과
  동일한 "완전성 사전 점검" 원칙을 Recording 계층 전반에 일관되게 적용했다.
- 새로 발견한 한계(원본 프레임을 무압축으로 버퍼링하는 메모리 비용이 다채널 환경에서
  비현실적임)는 숨기지 않고 FC-009로 등록하고 experiment.md Next Action에 압축 청크 버퍼링
  검토를 명시했다 — 정확성 문제(이번 PAR)와 배포 가능성 문제(FC-009)를 구분해 다음
  세션에서 이어갈 수 있게 했다.
