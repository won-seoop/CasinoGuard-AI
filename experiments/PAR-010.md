# PAR-010 Adaptive Recording Event Clip 재인코딩 낭비를 FFmpeg Stream Copy Hybrid 방식으로 개선

관련 실험: EXP-017, EXP-019

## 1. 한줄 요약
Event Clip을 원본 프레임부터 통째로 재인코딩해 Active Stream과 같은 내용을 두 번
인코딩하던 방식을, IDLE Tier와 겹치는 일부 구간만 재인코딩하고 나머지는 FFmpeg
Stream Copy로 오려내 이어붙이는 Hybrid 방식으로 바꿔, 완전성(511/511 프레임)을 그대로
유지하면서 Clip 생성 CPU 시간을 74.6~85.6% 줄였다.

## 2. 문제가 뭐였는가?
EXP-017에서 Event Clip을 포함한 총 저장량이 Baseline보다 오히려 47.7% 늘어나는
반직관적 결과가 나왔지만, 원인을 "재인코딩 구조"로 지목만 하고 실제 대안을 구현하지는
못한 채 Next Action으로 남겨뒀다. EXP-019에서 더 길고(1,600프레임) IDLE 비중이 훨씬 큰
(75%) 시나리오로 재검증하는 과정에서, Event Clip의 Pre-Roll(10초)이 Active Stream에는
아예 기록되지 않는 IDLE Tier 구간까지 파고드는 새로운 경계 사례(511프레임 중 112프레임,
21.9%)도 함께 발견했다 — 단순히 "Stream Copy로 바꾸면 끝"이 아니라, 그 경우 Naive
Stream Copy는 Clip이 조용히(에러 없이) 불완전해진다는 두 번째 문제가 있었다.

## 3. 왜 이 문제가 중요했는가?
카지노 CCTV에서 Event Clip은 보안 사고 증거 확보와 신속 재생을 위해 딜러/보안팀이
가장 자주 꺼내 보는 산출물이다. (1) 재인코딩 낭비는 다중 채널 환경에서 Event가 자주
발생할수록 CPU/저장 비용이 누적되는 Edge Device 관점의 문제이고, (2) Naive Stream
Copy의 조용한 불완전성은 더 심각하다 — 카지노에서 가장 흔한 패턴("한동안 조용하다가
갑자기 사람이 들어와 제한구역을 침범")일수록 Pre-Roll이 IDLE 구간까지 파고들 가능성이
크고, 하필 그 "사고 직전 몇 초"가 수사관이 가장 보고 싶어 하는 장면이다. 이 문제를
못 잡으면 Event Clip이 파일로는 정상 재생되니 자동화 파이프라인이 누락을 알아채지
못한 채 운영될 위험이 있다. Edge Camera(Active Stream 생성)와 NVR/VMS(Event Clip
추출·보관) 양쪽에 걸친 문제이기도 하다.

## 4. 원인이 뭐였는가?
`scripts/run_exp017_adaptive_recording.py`의 `write_adaptive()`를 코드로 직접 확인한
결과, Event Clip은 Active Stream 작성과 완전히 별개인 `cv2.VideoWriter`로 원본 프레임을
그대로 다시 write하고 있었다 — Active Stream에 이미 인코딩된 프레임을 픽셀부터 다시
인코딩하는 구조였다. EXP-019에서 `active_stream_positions()`와 `clip_window_all_active()`
(신규 추가, `src/recording/adaptive.py`)로 Clip 계획 구간 `[1089,1599]`를 직접 검사한
결과, 앞쪽 112프레임이 IDLE Tier(`[1089,1200]`)에 속해 Active Stream에 존재하지 않음을
확인했다 — Active Stream은 설계상 IDLE 프레임을 저장하지 않기 때문이다(추측이 아니라
`compute_tier_sequence`/`write_adaptive` 코드와 실제 tier 배열로 확인).

## 5. A를 고민하였는데 왜 안 했는가?
**A: Naive Stream Copy — Active Stream에서 Clip 구간 전체를 그대로 FFmpeg `-c copy`로
오려낸다.** CPU 비용이 사실상 0에 가까울 정도로(EXP-019 실측 0.0003초, 재인코딩 대비
1,000배 이상 빠름) 가장 저렴한 방법이었지만, IDLE 겹침이 있는 경우 Active Stream에
없는 프레임은 아예 복사할 수 없어 511프레임 중 112프레임(21.9%)이 누락된 "조용히
불완전한" Clip을 만든다는 것을 실측으로 확인해 단독 채택하지 않았다. 파일 자체는
정상적으로 열리고 재생되므로 이 누락은 육안 검토 없이는 드러나지 않는다는 점도
위험 요소로 판단했다.

## 6. B를 고민하였고 왜 적용했는가?
**B: Hybrid — IDLE Tier와 겹치는 구간만 원본 프레임에서 재인코딩하고, 나머지는 Active
Stream에서 Stream Copy로 오려낸 뒤 FFmpeg concat demuxer로 합친다.** A(전체 재인코딩)의
완전성과 B(Naive Copy)의 저비용을 모두 만족한다는 것이 핵심 근거였다. EXP-019에서 실제로
구현·측정한 결과, GOP=25(1초당 Keyframe 1개, 실무에 가까운 설정) 기준 CPU 시간이 전체
재인코딩 대비 0.467s→0.085s(-81.7%)로 줄면서도 511/511 프레임 완전성은 그대로
유지됐고, 파일 크기 증가도 +0.9%에 불과했다(재인코딩되는 부분이 112/511=21.9%뿐이라
전체 재인코딩과 크기가 거의 같다). 부수적으로, Active Stream의 GOP(Keyframe 간격)를
1(전부 Keyframe)과 25(1초당 1개)로 비교해 Stream Copy 절단 정확도와 연속 녹화 저장량의
Trade-off도 함께 확인했다: GOP=1은 절단이 정확하지만 연속 녹화 저장량이 6.3배
커져(Adaptive Recording의 원래 목적과 충돌) GOP=25를 기본값으로 권장했다 — 이때 발생하는
절단 오차(최대 ~1초)는 Keyframe 스냅으로 인해 "더 이르게" 잘리는 방향이라 보안 Event
Clip 맥락에서는 오히려 여유(추가 Pre-Roll)로 작용해 무해함을 별도 보조 실험으로
확인했다.

## 7. 어떤 방식으로 검증했는가?
EXP-010/014~018과 동일한 egress 제약으로 Wikimedia 원본 영상 대신 ultralytics 내장
`bus.jpg`에 Pan/Jitter를 적용한 합성 시나리오를 사용했다. EXP-017(900프레임, IDLE 33%)
보다 78% 긴 1,600프레임(64초) 시나리오를 새로 설계해 IDLE 비중을 75%로 크게 늘리고,
Pre-Roll이 IDLE 구간까지 파고들도록 NORMAL 구간을 Pre-Roll(250프레임)보다 짧은
100프레임으로 의도적으로 설계했다. Detection은 매 프레임 실제 YOLO11n(conf=0.4,
imgsz=640)+ByteTrack 추론 결과를 사용했다. FFmpeg 인코딩·Stream Copy·concat은
imageio-ffmpeg(PyPI)로 받은 정적 FFmpeg 7.0.2(libx264 포함) 바이너리로 수행했고,
프레임 수 검증은 ffprobe가 없어 rawvideo 디코딩 출력 바이트 수를 프레임 크기로 나눠
직접 계산했다(텍스트 로그 파싱 방식이 concat 출력에서 부정확함을 실측으로 확인하고
폐기). `src/recording/adaptive.py`에 순수 함수 2개(`active_stream_positions`,
`clip_window_all_active`)를 추가하고 `tests/test_adaptive_recording.py`에 Unit Test
8개를 추가했으며, 전체 `pytest tests/` 105 passed/7 skipped로 Regression Test를 완료했다
(EXP-017의 병합 로직 테스트를 포함해 기존 테스트는 전부 무수정 통과).

## 8. 개선된 수치적인 결과가 무엇이었는가?

| Metric (GOP=25, 511프레임 Clip 기준) | A: 전체 재인코딩 (기존, EXP-017 방식) | B: Naive Copy | C: Hybrid (신규 채택) |
|---|---|---|---|
| CPU 시간 | 0.467s | 0.0003s | 0.085s (**-81.7%** vs A) |
| Wall 시간 | 2.838s | 0.037s | 0.568s (**-80.0%** vs A) |
| 파일 크기 | 5,713,451 bytes | 4,722,960 bytes | 5,763,825 bytes (+0.9%) |
| 완전성 | 511/511 | **399/511 (112프레임 누락)** | 511/511 |

GOP=1(전부 Keyframe)에서도 동일 경향 재확인: A 0.433s → C 0.062s(**-85.6%**), 둘 다
511/511 완전.

|---|---|---|

## 9. 재발 방지 대책
- `clip_window_all_active()`를 Clip 생성 파이프라인의 필수 사전 점검 단계로 두도록
  experiment.md Decision에 명시했다 — IDLE 겹침이 없으면 순수 Stream Copy(가장 저렴)만
  사용하고, 겹침이 있을 때만 Hybrid 경로로 전환하는 정책이다.
- `tests/test_adaptive_recording.py`에 IDLE 겹침 유무를 모두 검증하는 테스트
  (`test_clip_window_all_active_false_when_preroll_dips_into_idle` 등)를 추가해, 향후
  Tier 로직이나 Pre-Roll 계산이 바뀌어도 이 경계 사례 판정이 회귀하면 즉시 실패하도록
  고정했다.
- 남은 한계를 정직하게 기록한다: 이번 실험은 IDLE 구간 원본 프레임을 결정론적 합성
  함수로 "재생성"해 Hybrid의 재인코딩 조각을 만들었다. 실제 카메라에서는 지나간 원본
  프레임을 재생성할 수 없으므로, 지침 23이 요구하는 Circular Buffer(최근 N초 고화질
  원본 프레임을 Tier와 무관하게 항상 보관)를 실제로 구현해야 Hybrid 방식이 프로덕션에서
  성립한다 — experiment.md Next Action으로 이월했다.
- EXP-019의 실험 스크립트(`scripts/run_exp019_event_clip_copy.py`)와 GOP 비교 보조
  스크립트를 재사용 가능한 형태로 남겨, 향후 GOP 값이나 Pre/Post-Roll 길이를 바꿀 때
  동일한 방식으로 재측정할 수 있게 했다.
