# PAR-014 Adaptive Recording/Circular Buffer를 실시간 파이프라인에 통합하며 Pre-Roll 추출 시점 설계 오류를 사전에 발견

관련 실험: EXP-023 (관련: EXP-017/PAR-008, EXP-019/PAR-010, EXP-020/PAR-011, EXP-021/PAR-012, EXP-022/PAR-013)

## 1. 한줄 요약
Adaptive Recording/Circular Buffer(EXP-017~022)를 처음으로 실제 Detection+Tracking+
BestShot+Metadata 실시간 단일 패스 파이프라인에 통합하면서, "EVENT 구간이 끝난 뒤 한꺼번에
Pre-Roll을 꺼내는" 더 단순한 설계(대안 A)가 이 프로젝트의 실제 시나리오에서 Pre-Roll의
47%(240/511프레임)를 잃어버린다는 것을 구현 전 실측으로 확인하고, "트리거 순간 즉시 꺼내는"
방식(대안 B)을 채택해 511/511 완전한 Event Clip을 만들었다.

## 2. 문제가 뭐였는가?
EXP-017~022는 전부 Adaptive Recording/Circular Buffer 로직을 독립된 스크립트로만
검증했다 — Detection 결과를 실시간으로 SQLite에 쌓는 `run_full_pipeline.py` 계열과는
한 번도 같은 루프에서 동작한 적이 없었고, Pre-Roll을 꺼내는 시점도 항상 스크립트에
`trigger_frame=1339`처럼 미리 하드코딩된 값으로만 테스트됐다(01. Architecture & Roadmap에
반복적으로 "아직 run_full_pipeline.py에 통합되지 않음"으로 남아 있던 항목). 실제로 두
시스템을 하나의 온라인 루프로 합치자, Event가 "언제" 발생할지 미리 알 수 없는 상태에서
Pre-Roll을 안전하게 꺼낼 수 있는 유일한 시점이 언제인지가 처음으로 실제 문제가 됐다.

## 3. 왜 이 문제가 중요했는가?
Event Clip은 카지노 CCTV에서 보안팀이 사고 직후 가장 먼저 꺼내 보는 증거 영상이다.
Pre-Roll(사고 10초 전)이 조용히 손실되면 "사고가 어떻게 시작됐는가"라는, 조사에서 가장
중요한 구간이 사라진다. 이 문제는 특히 카지노처럼 사람이 몰리는 구간에서 Intrusion이
짧은 간격으로 반복될 때(이번 실험처럼 두 차례 ENTER가 Post-Roll 간격보다 가깝게 겹쳐
EVENT Tier가 261프레임 동안 끊기지 않고 이어진 경우) 더 잘 드러난다 — 즉 "사람이 많고
사건이 잦은" 카지노 환경일수록 대안 A의 실패 조건에 더 쉽게 걸린다는 역설이 있다.
Edge Camera(프레임 캡처/버퍼링)와 NVR/VMS(Event Clip 추출·보관) 양쪽에 걸친 설계 문제이며,
FC-008(Naive Stream Copy가 조용히 불완전한 Clip을 만든 문제)과 근본적으로 같은 계열의
실수를 Circular Buffer 계층에서 반복할 뻔했다.

## 4. 원인이 뭐였는가?
`src/recording/circular_buffer.py`의 `required_capacity_for_pre_roll()`은 "Pre-Roll
길이(pre_roll_frames+1)"만 근거로 버퍼 용량을 계산한다 — "Event가 얼마나 오래 지속될 수
있는가"는 애초에 이 함수의 관심사가 아니었다. 이번 실험(EXP-023)에서 두 번의 Intrusion이
Post-Roll(250프레임)보다 가까운 간격(약 150~180프레임)으로 반복돼 EVENT Tier가 261프레임
연속으로 이어졌고, 그 261프레임 동안에도 Circular Buffer는 매 프레임 계속 push되어 오래된
프레임을 evict하고 있었다. 실험 종료 시점(frame 899)의 실제 Circular Buffer 상태를
`FrameCircularBuffer.coverage(389, 899)`로 직접 조회한 결과, `start_frame=389`부터
`628`까지 240프레임이 이미 버퍼에서 사라져 있었다 — 버퍼 용량(271)이 EVENT 지속
시간(261프레임)에 육박했기 때문에, "EVENT가 끝난 뒤" 꺼내려 했다면 Pre-Roll 시작 부분이
통째로 없었을 것임을 코드 실행 결과로 직접 확인했다(추측이 아니라 동일 실행의 buffer
객체를 대상으로 한 사후 조회).

## 5. A를 고민하였는데 왜 안 했는가?
**A: EVENT Tier 구간이 완전히 끝난 뒤(Post-Roll 만료 시점)에 Pre-Roll+본편 전체를 한 번에
Circular Buffer에서 꺼낸다.** 구현이 더 단순하다는 장점이 있다 — Clip 하나를 단일 호출로
완성할 수 있고, 여러 개의 ENTER가 병합되는 경우도 "끝난 뒤 한 번" 처리하면 되므로 상태
관리가 필요 없다. 그러나 이 실험에서 실제 버퍼 상태로 사후 검증한 결과 511프레임 중
240프레임(47.0%)이 이미 evict되어 있어 Pre-Roll을 복원할 수 없었다 — Circular Buffer
용량을 "EVENT Tier가 이론상 얼마나 길게 지속될 수 있는가"까지 고려해 몇 배로 늘리지 않는
한 근본적으로 성립하지 않는 방식이라고 판단해 채택하지 않았다(용량을 늘리는 것은
메모리 비용을 다시 키워 EXP-021/022의 개선을 무효화한다).

## 6. B를 고민하였고 왜 적용했는가?
**B: Tier가 IDLE/NORMAL에서 EVENT로 전환되는 바로 그 프레임(트리거 순간)에 즉시 Pre-Roll을
Circular Buffer에서 꺼내고, 이후 프레임은 실시간으로 들어오는 대로 Clip에 계속 이어
붙인다.** 이 시점은 Pre-Roll 구간(트리거 이전)이 버퍼에서 가장 최근에 존재를 보장할 수
있는 유일한 순간이다 — 트리거 이후로 시간이 지날수록 버퍼는 더 오래된 프레임부터
evict하므로, "더 일찍 꺼낼수록 더 안전하다"는 것이 핵심 근거다. 같은 EVENT 구간 안에서
추가 ENTER가 발생해도(이번 실험의 2번째 ENTER) 이미 열려 있는 Clip에 Track ID만
추가하면 되므로 EXP-017/PAR-008의 병합(Merge) 로직과 동일한 효과를 온라인 방식으로도
재현할 수 있었다. 실제로 4건의 ENTER가 Clip 1개로 병합되어 저장됐고, 511/511프레임
완전성이 유지됐다.

## 7. 어떤 방식으로 검증했는가?
- **Dataset**: EXP-017과 동일한 ultralytics 내장 `bus.jpg`(810×1080) + Pan/Jitter
  900프레임 3-Phase 시나리오(IDLE[0,300)/NORMAL[300,600)/EVENT[600,900), ROI 중앙
  대역 x=[430,620]). 이번 세션도 Wikimedia 원본 영상은 egress 차단으로 접근 불가.
- **환경/Configuration**: 원격 세션 `.venv`(Python 3.11.15), YOLO11n(conf=0.4,
  imgsz=640)+ByteTrack 실시간 추론(캐시 재사용 아님), pre_roll=10s/post_roll=10s
  (250프레임), `required_capacity_for_pre_roll(250, safety_margin=20)=271`,
  `TierQualityConfig(idle=50, normal=75, event=95)`(EXP-022 채택값).
- **Baseline**: 코드 레벨 통합 자체가 이전에 없었으므로, EXP-008(Metadata Pipeline
  단독 P95=41.8ms)과 EXP-021/022(Circular Buffer 단독 인코딩 비용)를 각각의 비교
  기준으로 사용했다.
- **비교 방식**: 같은 900프레임 실행 안에서 Detection+Tracking / ROI+BestShot+Metadata /
  Adaptive Recording+Circular Buffer 세 단계의 소요 시간을 프레임마다 별도로 측정해
  Circular Buffer가 추가하는 순수 오버헤드를 직접 분리했다. 대안 A/B는 같은 실행의
  실제 Circular Buffer 객체 상태로 사후 `coverage()` 조회를 통해 실측 비교했다(가정이
  아니라 실제 버퍼 상태 조회).
- **Regression Test**: `OnlineTierClassifier`(신규)가 기존에 검증된 `compute_tier_sequence`
  (Two-Pass)와 동일한 시퀀스에서 프레임 단위로 완전히 일치하는지 확인하는 회귀
  테스트(고정 케이스 5개 + 랜덤 시퀀스 20개)를 추가했고, `MetadataStore.add_event`/
  `update_event_detail`에 대한 단위 테스트도 추가했다. 전체 `pytest tests/`
  142 passed / 7 skipped(신규 10건 포함 149개 중)로 기존 테스트 전부 무수정 통과를
  확인했다.

## 9. 재발 방지 대책
- `run_exp023_pipeline_integration.py`에 대안 A의 실패를 `alternative_a_extract_at_run_end`
  필드로 `summary.json`에 항상 함께 기록하도록 구현했다 — 향후 Pre-Roll/Post-Roll 길이나
  Tier 정책이 바뀌어도 "그 설정에서 대안 A가 성립했는가"를 같은 실행에서 바로 확인할 수
  있다.
- `OnlineTierClassifier`가 기존 `compute_tier_sequence`와 어긋나면 즉시 실패하는 회귀
  테스트(`test_online_tier_classifier_matches_offline_*`)를 추가해, Tier 규칙이 이후
  수정되더라도 온라인/오프라인 두 구현이 갈라지는 것을 pytest 단계에서 잡는다.
- Event Clip이 Post-Roll 완료 전에 영상/세션이 끝나 잘리는 경우(`truncated_at_video_end`)를
  숨기지 않고 summary에 명시하도록 구현했다 — FC-008과 같은 "조용한 불완전성"을 Circular
  Buffer 계층에서도 반복하지 않기 위한 조치다.
- `required_capacity_for_pre_roll()`은 여전히 "Pre-Roll 길이"만 고려하고 "EVENT Tier
  최대 지속시간"은 고려하지 않는다는 한계를 experiment.md Next Action에 명시적으로
  남겼다 — 실제 배포 전에는 카지노 피크 시간대의 예상 최대 연속 Intrusion 지속시간을
  실측해 용량 계산식에 반영해야 한다.
