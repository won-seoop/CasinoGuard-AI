# PAR-015 VMS Search API가 Event Clip 경로를 노출하지 못한 계층 간 간극 수정

관련 실험: EXP-023(Adaptive Recording+Circular Buffer 실시간 통합, PAR-014), EXP-024(VMS Search
API event_clip_path 응답 필드 + Event Clip 재생 엔드포인트)

## 1. 한줄 요약
VMS Search API가 Metadata Store의 JSON 파싱 로직을 재사용하지 않고 raw SQL로 `detail`을
그대로 반환해(FC-011) `event_clip_path`가 문자열 안에 숨어 있고 영상 재생 엔드포인트 자체가
없었던 문제를, `MetadataStore.query_events()`를 재사용하도록 API를 고치고
`GET /events/{id}/clip` 엔드포인트를 추가해 해결했다 — 실제 EXP-023 산출물(Event Clip
27MB)로 end-to-end 재생까지 확인했다.

## 2. 문제가 뭐였는가?
EXP-023(PAR-014)에서 `MetadataStore.update_event_detail()`로 Event의 `detail` JSON에
`event_clip_path`를 붙이는 기능을 이미 구현했는데도, `src/api/main.py`의 `/events`와
`/tracks/{track_id}`는 `MetadataStore`를 쓰지 않고 자체 `sqlite3.connect()` + `SELECT *`를
썼다. 그 결과 `detail` 컬럼이 JSON으로 파싱되지 않은 **문자열 그대로** 응답에 포함됐고,
`event_clip_path`를 쓰려면 클라이언트가 직접 `json.loads()`해야 했다. 더 나아가 그 경로를 알아도
실제 영상 파일을 받아올 수 있는 엔드포인트(`GET /events/{id}/clip` 같은)가 전혀 없었다 —
지침 17이 요구하는 "특정 Event 전후 영상"을 API가 제공하지 못하는 상태였다.

## 3. 왜 이 문제가 중요했는가?
VMS(Video Management System)의 핵심 가치는 "AI가 찾아낸 Event를 사람이 실제로 확인할 수 있게
하는 것"이다. 카지노처럼 Intrusion/Loitering/Line Crossing Event가 보안 담당자의 즉각적인
확인을 요구하는 환경에서, Event를 검색해도 그 순간의 영상을 재생할 방법이 없다면 Metadata
검색 자체가 실무적으로 무의미해진다(지침 17: "결과 표시: BestShot, Timestamp, Track ID, Event
Type, Camera ID, **Video 위치**"). 이 문제는 단일 기능 버그가 아니라, **Metadata 스키마가
확장될 때마다 반복될 수 있는 설계 패턴의 문제**였다 — 지침 19의 Attribute Metadata
(`upper_color`/`lower_color`/`bag`/`hat`)도 유사하게 `detail`류 JSON에 필드를 추가하는
방식을 쓸 가능성이 높으므로, API가 Store를 거치지 않고 자체 SQL을 유지하는 한 똑같은 "Store는
맞는데 API가 노출 안 함" 간극이 다시 발생할 수 있다.

## 4. 원인이 뭐였는가?
`src/api/main.py`를 직접 읽어 확인했다: `/events`와 `/tracks/{track_id}`가
`conn.execute("SELECT * FROM events ...")` 후 `dict(row)`만 호출하고 `json.loads()`를 호출하는
코드가 없었다(코드 인용: EXP-024 experiment.md Baseline 참고). 반면 `src/metadata/store.py`의
`MetadataStore.query_events()`는 이미 `detail`을 `json.loads()`로 파싱하고 있었다 — 즉 올바른
로직이 Store 레벨에는 존재했지만 API가 그것을 재사용하지 않고 독자적인 raw SQL 경로를 유지한
것이 직접적인 원인이었다. `tests/test_api.py`가 `event_clip_path`를 전혀 검증하지 않았던 것도
이 간극이 한 세션 넘게 감지되지 않은 이유다(테스트 커버리지 공백, 추측이 아니라 실제
`git log`/코드 검토로 확인).

## 5. A를 고민하였는데 왜 안 했는가?
**대안 A: API의 각 엔드포인트에서 `detail` 문자열을 그 자리에서 `json.loads()`해 수동으로
`event_clip_path`를 꺼낸다.** 구현이 더 작고 `MetadataStore`를 건드리지 않는다는 장점이 있다.
하지만 이미 Store에 존재하는 JSON 파싱 로직을 API에 다시 구현하는 것이므로 중복이고, 이번
문제의 근본 원인(두 곳에 같은 로직이 따로 존재해 한쪽만 고쳐지는 것)을 그대로 남겨 둔다 —
다음에 또 다른 필드(Attribute Metadata 등)가 추가되면 API 쪽 수동 파싱을 또 빠뜨릴 위험이
크다. Edge 적용 가능성이나 Latency 측면에서는 A/B 차이가 없어(둘 다 SQLite 단일 쿼리 수준),
유지보수성 기준으로만 기각했다.

## 6. B를 고민하였고 왜 적용했는가?
**대안 B(채택): `/events`와 `/tracks/{track_id}`가 `MetadataStore.query_events()`를 그대로
재사용하도록 API를 고치고, `query_events()` 자체에 `event_clip_path`를 최상위 필드로 노출하는
로직과 `has_clip` 필터를 추가한다.** 이미 `tests/test_metadata_store.py`가 검증하는 단일
구현을 API가 그대로 쓰게 되어 중복이 사라지고, Store 쪽에 한 번만 로직을 넣으면 API/다른
스크립트 어디서 호출하든 동일하게 동작한다는 보장이 생긴다. 추가로 `GET /events/{event_id}/clip`
엔드포인트를 신설해 경로 문자열이 아니라 실제 영상 바이트(`FileResponse`, `video/mp4`)를
돌려주도록 했다 — "영상 위치를 안다"와 "영상을 재생할 수 있다"는 다른 요구사항이고, 지침 17은
후자를 요구한다고 판단했다.

## 7. 어떤 방식으로 검증했는가?
- **Dataset**: `data/raw/bus.jpg`(ultralytics 내장) + EXP-017/EXP-023과 동일한 900프레임
  3-Phase(IDLE/NORMAL/EVENT) 합성 시나리오. 이 원격 세션도 Wikimedia 등 외부 일반 도메인이
  egress 정책상 차단되어(`curl commons.wikimedia.org` → 403 재확인) 원본
  `crowded_intersection_1080p.webm`을 쓸 수 없었다(EXP-010부터 반복된 동일 제약, 정직하게
  기록). `yolo11n.pt`는 GitHub Release Asset으로 정상 다운로드됨.
- **환경**: 원격 자동화 세션, `.venv`(Python 3.11.15) 신규 생성, CPU 전용.
- **실제 재현**: `scripts/run_exp023_pipeline_integration.py`를 코드 수정 없이 그대로 재실행해
  실제 YOLO11n+ByteTrack 검출이 반영된 `results/EXP-023/metadata.db`(Track 10개, Event 8개
  — ENTER 4/EXIT 4)와 `event_clips/event_clip_1.mp4`(27,033,338 bytes)를 재생성했다.
- **End-to-End 수동 검증**: `fastapi.testclient.TestClient`로 API의 `DB_PATH`만 이 실제 DB로
  바꿔 `GET /events`, `GET /events?has_clip=true|false`, `GET /events/{id}/clip`,
  `GET /tracks/1`, `GET /`(Dashboard)를 직접 호출해 응답을 눈으로 확인했다.
- **pytest(결정론적, YOLO 재실행 불필요)**: `tests/test_api_event_clip.py`(신규 8개) +
  `tests/test_metadata_store.py`(신규 3개)가 `MetadataStore`로 만든 작은 fixture DB를 대상으로
  필드 노출/필터/파일 서빙/404 네 가지 경로(클립 없음, event_id 없음, 파일이 디스크에 없음)를
  검증한다.
- **Regression Test**: `python3 -m pytest tests/ -q` 전체 153 passed / 7 skipped(기존에도
  `results/metadata_pipeline/metadata.db` 부재로 skip되던 테스트, 이번 변경으로 새로 생긴
  skip 아님) — 기존 Unit Test 전체가 그대로 통과함을 확인했다.

## 8. 개선된 수치적인 결과가 무엇이었는가?
수정 전/후는 "정량 Metric"이 아니라 "기능 충족 여부"로 검증했다(정확하게 측정할 수 없는 지표를
억지로 만들지 않음, 지침 31):

| 항목 | Before | After |
|---|---|---|
| `GET /events` 응답의 `detail` | JSON 미파싱 문자열 (`"{\"zone\": ..., \"event_clip_path\": ...}"`) | `dict`로 파싱 + `event_clip_path` 최상위 필드 (`"results/EXP-023/event_clips/event_clip_1.mp4"`) |
| `event_clip_path` 유무로 Event 필터링 | 불가능 | `?has_clip=true\|false` 지원, 실측 ENTER 4건/EXIT 4건으로 정확히 분리 |
| Event Clip 실제 재생/다운로드 | 엔드포인트 없음(404, 라우트 부재) | `GET /events/{id}/clip` → 200, `video/mp4`, 27,033,338 bytes(실제 파일과 byte-for-byte 일치) |
| 클립 없는 Event 조회 시 동작 | (해당 엔드포인트 자체가 없었음) | 404 `{"detail": "no clip recorded for this event"}` |
| pytest 커버리지 | event_clip_path 관련 테스트 0개 | 신규 11개(Store 3 + API 8), 전체 153 passed/7 skipped(기존 skip 유지, 회귀 없음) |

## 9. 재발 방지 대책
- `tests/test_api_event_clip.py`를 Regression Test로 유지한다 — API가 다시 raw SQL로
  되돌아가 `detail` 파싱을 건너뛰면 `test_list_events_exposes_event_clip_path_top_level`이
  즉시 실패한다.
- Decision(EXP-024): API가 새 Metadata 필드를 노출할 때는 반드시 `MetadataStore`의 쿼리
  메서드를 거친다 — raw SQL을 API 레이어에 별도로 유지하지 않는다. 지침 19 Attribute
  Metadata(`upper_color`/`lower_color`/`bag`/`hat`) 구현 시 이 원칙을 그대로 적용해 같은
  계층 간 간극이 재발하지 않도록 한다.
- `GET /events/{event_id}/clip`이 "경로는 있지만 파일이 디스크에 없는" 경우를 조용히 500으로
  죽지 않고 명시적 404로 처리하도록 테스트(`test_get_event_clip_404_when_clip_file_missing_on_disk`)로
  고정해 뒀다 — Circular Buffer/Clip 파일이 아직 비동기로 완성되지 않은 시점에 조회가 들어와도
  안전하게 처리된다.
