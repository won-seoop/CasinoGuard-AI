# PAR-002 Intrusion EXIT 이벤트 유실 수정 (Track 소실 시 강제 종료 처리)

관련 실험: EXP-005, EXP-007

## 1. 한줄 요약
Track이 ROI 안에 있는 상태에서 사라지면 EXIT 이벤트가 발생하지 않는 문제(ENTER 16 vs EXIT 7)를 발견하고, `forget_track()`이 INSIDE 상태였던 Track에 대해 EXIT 이벤트를 강제로 발생시키도록 수정했다.

## 2. 문제가 뭐였는가?
EXP-005에서 300프레임 동안 ENTER 이벤트는 16건 발생했는데 EXIT 이벤트는 7건뿐이었다. Track이 Occlusion이나 화면 이탈로 사라지면 `forget_track()`이 상태만 삭제하고 EXIT 이벤트는 만들지 않았기 때문이다.

## 3. 왜 이 문제가 중요했는가?
VMS Search 관점에서 "이 사람이 언제 통제구역에서 나갔는가"를 조회할 수 없다는 뜻이다. 카지노에서는 금고·VIP룸 등 통제구역에 누가 얼마나 있었는지가 보안 기록의 핵심인데, EXIT 기록이 없으면 "체류 시간"과 "무단 진입 지속 여부"를 판단할 근거 자체가 사라진다. 또한 Phase 7 Loitering의 Dwell Time 계산도 ROI를 벗어난 시점을 알아야 정확히 종료되므로, 이 버그를 방치하면 Loitering 로직에도 영향이 이어질 수 있었다.

## 4. 원인이 뭐였는가?
`ROIStateMachine.forget_track()` 구현이 "Track 상태 정리(메모리 관리)"라는 책임만 가지고 설계되어, 상태가 INSIDE였는지 확인하고 EXIT를 발생시키는 책임이 빠져 있었다. EXP-005의 이벤트 카운트(ENTER 16, EXIT 7)를 통해 비대칭을 발견했다.

## 5. A를 고민하였는데 왜 안 했는가?
"지금은 손대지 않고 알려진 한계로만 남긴다"(EXP-005 최초 Decision)를 먼저 검토했다. 구현 비용이 0이라는 장점이 있었지만, VMS Search에서 EXIT 기록 조회가 실제로 불가능해지는 실무적 문제였고 Loitering 로직 설계에도 영향을 주므로 다음 Phase(7)로 미루되 반드시 고치기로 했다(EXP-005 Decision에 명시).

## 6. B를 고민하였고 왜 적용했는가?
`forget_track(track_id, frame_idx)`가 삭제 직전 상태를 확인해서, INSIDE였다면 `ROIEvent(EXIT)`를 반환하도록 수정했다(대안 B). 별도 백그라운드 타이머나 복잡한 상태 없이, 기존 호출 지점(Track 소실 판정 시 `forget_track` 호출)에 frame_idx 인자만 추가하면 되어 구현이 단순하고 기존 구조(OUTSIDE/INSIDE state)와 자연스럽게 맞았다.

## 7. 어떤 방식으로 검증했는가?
- Unit Test 2개 추가: `test_forget_track_emits_exit_when_was_inside`(INSIDE였던 Track이 사라지면 EXIT 발생), `test_forget_track_emits_nothing_when_was_outside`(OUTSIDE였던 Track은 이벤트 없음)
- 기존 Intrusion 관련 Unit Test(7개)가 모두 그대로 통과하는 것을 확인해 회귀가 없음을 검증(Regression Test 성격)

## 8. 개선된 수치적인 결과가 무엇이었는가?
이번 수정은 EXP-005의 과거 실행 결과를 다시 돌려 Before/After 수치로 비교하지는 않았다(EXP-005는 이미 완료된 실험으로 유지하고, 수정 사항은 코드 레벨 Unit Test로만 검증). 정성적으로는: 이 수정 이후 새로 실행하는 모든 Intrusion 감지에서 Track 소실 시 EXIT가 항상 함께 기록되므로, "ENTER는 있는데 EXIT가 없는" 데이터 정합성 문제가 구조적으로 해소되었다.

## 9. 재발 방지 대책
- Unit Test 2개를 추가해 향후 `forget_track` 로직을 변경해도 회귀가 발생하면 즉시 테스트가 실패하도록 함
- 상태를 가지는 이벤트 로직(State Machine)을 새로 만들 때는 "상태 삭제"와 "상태 전이 이벤트 발생"을 분리해서 생각하지 않고, 삭제 시점도 하나의 전이로 취급해 이벤트 발생 여부를 항상 검토하는 체크리스트를 experiments/_templates에 남김(다음에 Line Crossing/Loitering류 로직을 또 만들 때 동일 실수 방지)
