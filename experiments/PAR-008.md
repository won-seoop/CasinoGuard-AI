# PAR-008 Adaptive Recording Event Clip 중복 저장 문제 개선

관련 실험: EXP-017

## 1. 한줄 요약
서로 가까운 시간에 발생한 두 Intrusion Event를 Event마다 독립적인 Clip으로 각각
Pre/Post-Roll 확장해 저장하면 Window가 겹쳐 같은 프레임이 여러 Clip 파일에 중복
저장되는 문제를, 겹치거나 인접한 Window를 하나로 병합하는 방식으로 개선해
361프레임(41.4%)의 중복 저장을 0으로 만들었다.

## 2. 문제가 뭐였는가?
Adaptive Recording(지침 23)의 Event Clip 기능(Event -10초~+10초)을 구현하면서, "Event가
발생할 때마다 그 Event의 Pre/Post-Roll Window를 독립적인 Clip 파일로 저장한다"는 가장
단순한 방식(대안 A)을 먼저 구현했다. EXP-017의 합성 시나리오(bus.jpg + Pan, ROI 중앙
대역)에서 사람 무리가 ROI를 두 번 들락날락해 Intrusion Event가 두 번(`[639,714]`,
`[789,863]`) 발생했는데, 두 Event 사이 간격(74프레임 ≈ 3초)이 Post-Roll(250프레임=10초)
보다 짧았다. 이 조건에서 대안 A로 Clip을 계획하면 두 Event의 Window가 `[389,899]`와
`[539,899]`로 계산되어 두 번째 Window가 첫 번째 Window에 완전히 포함되는 것을
`plan_event_clips()`로 직접 계산해 확인했다.

## 3. 왜 이 문제가 중요했는가?
카지노 CCTV에서는 같은 사람이 입구 근처에서 머뭇거리다 들어왔다 나갔다를 반복하거나,
비슷한 시간대에 여러 사람이 연이어 같은 ROI에 드나드는 경우가 흔하다(예: 게이밍
플로어 입구, 카운트룸 앞). 이런 상황마다 독립적인 Clip을 만들면 (1) 저장 공간이
불필요하게 낭비되고, (2) Forensic 검색 시 하나의 연속된 사건이 여러 조각의 겹치는
Clip 파일로 쪼개져 있어 수사관이 같은 장면을 여러 번 확인해야 하는 불편이 생긴다.
장시간 운영되는 다중 채널 환경에서는 이런 중복이 누적되어 저장 용량과 검색 효율
양쪽에 계속 영향을 준다.

## 4. 원인이 뭐였는가?
`plan_event_clips()`의 최초 구현(대안 A)은 각 Event Interval을 정렬한 뒤 Pre/Post-Roll을
적용해 독립적인 Window로 그대로 반환하고, Window끼리 겹치는지 여부를 전혀 확인하지
않았다. EXP-017에서 두 Event Window(`[389,899]`, `[539,899]`)를 직접 출력해 완전히
겹친다는 것을 확인했고(코드 분석 + 실제 계산값 근거, 추측이 아님), `total_planned_frames()`
로 두 Window의 총 프레임 수를 합산하면 872프레임인데 실제 유효 구간은 511프레임뿐이라는
것도 함께 확인했다(361프레임=41.4%가 중복).

## 5. A를 고민하였는데 왜 안 했는가?
**대안 A: Event마다 독립적인 Clip 파일 생성(병합 없음)**. 구현이 가장 단순하고, Clip
파일과 Event가 1:1로 대응되어 "이 Clip이 어떤 Event 때문에 생성됐는지" 추적하기 쉽다는
장점이 있다. 하지만 (1) Event가 짧은 간격으로 반복되면 Window가 겹쳐 저장 공간을
불필요하게 낭비하고(이번 실험에서 41.4% 중복 실측), (2) Forensic 검색 화면에서 같은
시간대 장면이 여러 Clip으로 쪼개져 사용자 경험이 나빠지며, (3) Event가 세 번 이상
연달아 발생하면 낭비 비율이 더 커질 것으로 예상되어(이번 실험은 2건까지만 확인) 채택하지
않았다.

## 6. B를 고민하였고 왜 적용했는가?
**대안 B: 겹치거나 인접한(맞닿은) Window를 하나의 Clip으로 병합**. Event들을 시작
시각 순으로 정렬한 뒤, 새 Window의 시작이 지금까지 병합 중인 Clip의 끝 + `merge_gap_frames`
이내이면 같은 Clip으로 합치고(끝 시각은 더 큰 값으로 확장), 그렇지 않으면 새 Clip을
시작하는 방식으로 구현했다(`src/recording/adaptive.py::plan_event_clips`). `merge_gap_frames`를
매개변수로 두어 0(겹치거나 맞닿으면 병합, 채택 기본값)과 매우 작은 음수(병합 없음, 대안
A 재현)를 같은 함수로 표현할 수 있게 했다 — 이 설계 덕분에 대안 A/B를 서로 다른 코드
경로가 아니라 같은 함수의 파라미터 차이로 비교할 수 있었고, 실제로 EXP-017에서 두
결과를 나란히 계산해 대안 B가 저장 프레임 수를 872→511로 줄이는 것을 직접 확인했다.
A보다 구현 복잡도가 크게 늘지 않으면서 중복을 원천적으로 제거하고, 실제 시스템의
Event Clip 파일(`event_clip_0.mp4`)이 두 Event를 모두 포함하는 하나의 연속된 영상으로
남아 Forensic 검색 시에도 자연스럽다는 점에서 B를 선택했다.

## 7. 어떤 방식으로 검증했는가?
- **단위 테스트(순수 함수, I/O 없음)**: `tests/test_adaptive_recording.py`에 `plan_event_clips`
  대상 테스트 5개 추가 — Pre/Post-Roll 확장, 영상 시작/끝 경계 Clamp, 병합 발생 조건,
  병합 미발생 시(대안 A) 총 프레임 수가 병합 시(대안 B)보다 많다는 것, Event가 없을 때
  빈 리스트 반환. `compute_tier_sequence`/`should_keep_idle_frame`/
  `event_intervals_from_active_flags` 대상 테스트 14개도 함께 추가해 총 19개 신규
  테스트, 기존 76개(스킵 7개 제외) 포함 전체 95개 통과(회귀 없음).
- **통합 실험(EXP-017)**: bus.jpg + Pan/Jitter로 만든 900프레임(36초) 합성 시나리오에서
  실제 YOLO11n+ByteTrack+ROIStateMachine을 실행해 진짜 Intrusion Event 2건을 발생시키고,
  그 Event Interval을 `plan_event_clips()`에 `merge_gap_frames=0`(대안 B)과
  `merge_gap_frames=-1,000,000`(대안 A, 사실상 병합 안 함)으로 각각 넣어 결과를 비교했다.
  실제로 대안 B로 생성한 Event Clip 파일(`event_clip_0.mp4`, 511프레임, 15.2MB)이
  계획대로 프레임 손실 없이 저장되었는지도 `actual_frames_written`을 직접 세어 확인했다
  (기대 511 = 실제 511, 누락 0).
- Baseline: 항상 30(가정 25)fps 고화질로 전부 저장하는 기존 방식과 저장 용량도 함께
  비교했다(연속 녹화만 기준 18.7% 절감 — Event Clip 포함 시에는 오히려 47.7% 증가하는
  역전 현상도 함께 실측해 정직하게 기록함, EXP-017 Analysis 4번 참고).

## 8. 개선된 수치적인 결과가 무엇이었는가?

| Metric | 대안 A (병합 없음) | 대안 B (병합, 채택) |
|---|---|---|
| Event Clip 파일 수 | 2 | 1 |
| 총 저장 계획 Frame 수 | 872 | 511 |
| 중복 저장 Frame 수 | 361 (41.4%) | 0 |

| Metric | Before(Baseline) | After(Adaptive 연속 녹화) |
|---|---|---|
| 저장 용량 | 22,836,795 bytes | 18,560,969 bytes (−18.7%) |
| 기록 Frame 수 | 900 | 660 (idle 61 + active 599) |

(반대 방향 결과도 숨기지 않고 기록: Event Clip까지 포함한 총 저장량은 33,734,073 bytes로
Baseline 대비 오히려 +47.7% 많았다 — Pre/Post-Roll 20초가 36초짜리 데모 영상 전체의
절반 이상을 차지하는 시간 축 압축 때문이며, 실제 장시간 운영 환경에서는 재검증이
필요한 한계로 남긴다.)

## 9. 재발 방지 대책
- `plan_event_clips`를 pytest로 고정 회귀 테스트해두어, 이후 Pre/Post-Roll 계산이나
  병합 조건을 수정할 때 병합 로직이 깨지면 즉시 실패하도록 했다.
- Event Clip Plan과 실제 저장된 Frame 수(`actual_frames_written` vs `expected_frames`)를
  EXP-017 스크립트가 항상 함께 기록하도록 해, 향후 Config(Pre/Post-Roll, merge_gap)를
  바꿀 때마다 Event Clip 누락 여부를 자동으로 확인할 수 있게 했다.
- Config(`AdaptiveRecordingConfig`)로 `pre_roll_sec`/`post_roll_sec`/`merge_gap_sec`/
  `idle_frame_stride`를 관리해(지침 35) 값 변경 시 코드 여러 곳을 찾아 고치지 않아도
  되게 했다.
- "Event Clip 포함 총 저장량이 역전될 수 있다"는 한계를 experiment.md에 정직하게
  남겨, 다음 세션이 실제 장시간 영상으로 재검증하기 전까지 이 Pre/Post-Roll 기본값을
  프로덕션에 그대로 확정하지 않도록 Next Action에 명시했다.
