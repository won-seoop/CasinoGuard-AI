# PAR-012 Circular Buffer 원본 프레임 무압축 저장의 메모리 비용 문제 해결

관련 실험: EXP-020 (Circular Buffer Baseline, PAR-011), EXP-021 (JPEG 압축 청크 버퍼링, FC-009)

## 1. 한줄 요약
Adaptive Recording Circular Buffer가 원본 BGR 프레임을 무압축으로 버퍼링해 채널당
628~753MB(Pre-Roll 10초 기준)가 필요했던 문제를, 자료구조는 그대로 두고 push/pop
경계에서 JPEG 인코딩/디코딩만 추가해 quality=85 기준 메모리 90.8% 절감(72.47MB/채널)하면서
완전한 Event Clip(251/251 프레임)과 사실상 무손실에 가까운 화질(평균 픽셀 오차 2.61/255)을
그대로 유지했다.

## 2. 문제가 뭐였는가?
EXP-020에서 지침 23(Circular Buffer)을 실제로 구현하며 `memory_bytes()`로 실측한 결과,
Pre-Roll을 완전히 보장하는 최소 용량(251프레임)만 유지해도 810×1080 해상도 1채널 기준
628.21MB, 운영 여유분(301프레임)은 753.35MB가 필요했다. 카지노 CCTV는 채널이 수백 개
규모(CLAUDE.md 지침 8)인데, 이 방식을 그대로 채널마다 적용하면 100채널만으로도
62.8~75.3GB RAM이 필요해 Edge Camera/NVR에 전혀 현실적이지 않았다. 이 문제는 EXP-020에서
FC-009로 등록만 되고 해결되지 않은 채 이월된 상태였다.

## 3. 왜 이 문제가 중요했는가?
Circular Buffer는 Adaptive Recording(EXP-017)이 Event Clip의 Pre-Roll(사고 발생 전
10초)을 원본 화질로 복구하기 위한 핵심 부품이다(EXP-019/PAR-010에서 발견한 FC-008, "Naive
Stream Copy는 IDLE 겹침 구간을 조용히 누락시킨다"의 근본 해결책으로 EXP-020에서 도입됨).
그런데 그 해결책 자체의 메모리 비용이 다채널 배포에서 비현실적이라면, "정확하게 동작하는
설계"와 "실제로 배포 가능한 설계"가 분리되어 이 프로젝트가 목표로 하는 Edge Camera/NVR
배포 관점의 신뢰성을 잃는다. 카지노 환경에서는 채널 수가 많고(수백 대), 사고 조사에
필요한 Pre-Roll 화질이 낮으면 안 되므로, "메모리를 줄이되 화질을 지킨다"는 이 문제는
Adaptive Recording 전체 기능의 배포 가능성을 좌우하는 문제였다. 연쇄 영향: Circular
Buffer 메모리 비용 과다 → 다채널 NVR 메모리 예산 초과 → Adaptive Recording 자체를
포기하거나 채널 수를 줄여야 함 → Event Clip 완전성(FC-008 해결)이라는 이전 성과가
실제 배포 단계에서 무력화됨.

## 4. 원인이 뭐였는가?
`FrameCircularBuffer`가 push()된 프레임을 디코드된 raw ndarray 그대로 dict에 보관하도록
구현되어 있었다(EXP-020, `memory_bytes()` 실측으로 확인). 810×1080 BGR uint8 프레임은
1장에 2,624,400 bytes이며, 이는 코드/데이터로 직접 확인된 구조적 원인이지 추측이 아니다 —
`buf.memory_bytes(frame_nbytes)` 호출 결과가 capacity × frame_nbytes와 정확히 일치함을
EXP-020에서 이미 검증했다.

## 5. A를 고민하였는데 왜 안 했는가?
**대안 A: 버퍼에 저장할 프레임 자체의 해상도를 낮춘다(예: 0.5배 다운스케일 후 raw로
저장)**. 장점은 구현이 매우 단순하고(cv2.resize 한 줄) 인코딩/디코딩 CPU 비용이 전혀
없다는 점이다. 하지만 EXP-021에서 실제로 측정한 결과, capacity=301 기준 다운스케일
raw 버퍼는 197.49MB가 필요했는데, 이는 JPEG quality=30(28.08MB)보다도 7배 더 큰
메모리를 쓰면서 업스케일 후 화질(평균 픽셀 오차 9.10/255)은 JPEG q30(오차 6.59)보다도
나빴다. 더 결정적인 문제는, 다운스케일은 해상도 자체를 절반으로 줄이므로 저장 시점에
버려진 픽셀 정보는 나중에 어떤 방법으로도 복구할 수 없다는 점이다 — 카지노 사고 조사에서
화면을 확대해 얼굴이나 카드 숫자를 확인해야 하는 상황이 실제로 발생할 수 있는데, 이
대안은 그 요구를 원천적으로 충족할 수 없다. 메모리·화질·복구 가능성 세 기준 모두에서
대안 B에 열등해 채택하지 않았다.

## 6. B를 고민하였고 왜 적용했는가?
**대안 B: 프레임을 원본 해상도 그대로 JPEG로 압축해 버퍼에 저장하고, 꺼낼 때 디코드한다.**
`FrameCircularBuffer`가 이미 Generic(`FrameT`)으로 설계되어 있었기 때문에(EXP-020에서
"자료구조는 압축/파일 I/O를 모르게" 설계한 결정이 미리 되어 있었음), 자료구조를 전혀
바꾸지 않고 push 직전/get_range 직후 경계에서만 인코딩·디코딩을 추가하면 됐다. 원본
해상도를 그대로 유지하므로 복구 불가능한 정보 손실이 없고(다운스케일과 달리 quality로
손실 정도를 조절 가능), 실측 결과 quality=85에서 메모리 90.8% 절감과 사실상 무시할 수
있는 화질 손실(평균 픽셀 오차 2.61/255)을 동시에 달성했다. A보다 구현 복잡도가 약간
높지만(인코딩/디코딩 함수 추가), 메모리·화질·복구 가능성 모든 기준에서 우월해 채택했다.

## 7. 어떤 방식으로 검증했는가?
- Dataset: EXP-019/020과 동일한 합성 시나리오(ultralytics 번들 `bus.jpg` + Pan/Jitter,
  1,600프레임 중 IDLE 75%). Detection은 EXP-019가 실제 YOLO11n+ByteTrack으로 추론해
  캐시해 둔 `results/EXP-019/detection_cache.json`을 재사용(같은 입력 재추론은 낭비).
- Environment: `.venv311`(Python 3.11.15), opencv-python-headless 5.0.0, numpy 2.4.6,
  imageio-ffmpeg(정적 FFmpeg 7.0.2/libx264), pytest 9.1.1.
- Configuration: capacity 시나리오 4개(64/250/251/301, EXP-020과 동일), JPEG quality
  5개(30/50/70/85/95), 다운스케일 비교 1개(0.5배).
- Metric: 버퍼 메모리 사용량(`total_bytes()`, 신규 구현), Coverage 완전성(`coverage()`,
  기존 로직 재사용, 압축 여부와 무관함을 확인), encode/decode CPU 시간(5회 반복 평균,
  단발 측정의 노이즈를 실측으로 확인 후 방법론 수정), 평균 픽셀 절대오차(MAE), 최종
  Event Clip Pre-Roll 구간의 프레임 수/파일 크기.
- Baseline: EXP-020의 raw ndarray 버퍼(capacity=251/301에서 628.21MB/753.35MB).
- 비교 방식: 동일 시나리오·동일 capacity 시나리오에서 raw vs JPEG 5개 quality vs
  다운스케일 대안을 나란히 측정.
- Regression Test: `tests/test_circular_buffer.py`(기존 12개 + 신규 `total_bytes()`
  테스트 2개)와 `tests/test_frame_codec.py`(신규 7개, encode/decode roundtrip·품질별
  크기·손상 데이터 예외·`FrameCircularBuffer[bytes]` 통합)를 포함해 전체 pytest
  126 passed, 7 skipped(무관한 API 테스트) 확인 — 기존 테스트 전부 무수정 통과.

## 8. 개선된 수치적인 결과가 무엇이었는가?

| Metric (capacity=301, 1채널 기준) | Before (raw) | After (JPEG q85) |
|---|---|---|
| 메모리 사용량 | 789.94 MB (753.35 MiB) | 72.47 MB |
| 메모리 절감률 | - | 90.8% |
| Event Clip Pre-Roll 완전성 | 251/251 | 251/251 (동일) |
| 평균 픽셀 오차(MAE, 0~255) | 0 (원본) | 2.61 |
| Pre-Roll Clip 파일 크기 | 2,583,225 bytes | 3,073,411 bytes* |
| 100채널 환산 메모리(capacity=301) | ≈75.3 GB | ≈7.2 GB |

*Clip 파일 크기 자체는 q85에서 약간 늘었지만(원본 대비 +19%), 반대로 q95에서는
2,510,558 bytes로 raw보다 오히려 **작았다** — JPEG 재압축이 원본의 미세한 고주파
잡음을 일부 제거해 h264 인코더의 엔트로피 부담을 줄였기 때문으로 보인다(추측이 아니라
파일 크기·CPU 시간 실측치로 확인, EXP-021 Result 4번/Analysis 5번 참고). 이는 가설을
세울 때는 예상하지 못했던 결과라 정직하게 함께 기록한다.

Capacity Off-by-One(250 vs 251에서 정확히 frame 1089 하나만 누락) 특성은 quality와
무관하게 EXP-020과 동일하게 재현되어, "완전성 보장 로직은 그대로 두고 저장 방식만 바꾼다"는
설계 의도가 실제로 성립함을 확인했다.

## 9. 재발 방지 대책
- Regression Test: `tests/test_circular_buffer.py`/`tests/test_frame_codec.py`를
  CI 없이도 `PYTHONPATH=src pytest tests/`로 상시 실행 가능하도록 추가(총 19개 신규 케이스).
- 신규 발견한 설계 결함(`memory_bytes()`가 균일 프레임 크기를 가정해 가변 크기 압축
  프레임에는 부정확)을 `total_bytes(size_fn)`으로 별도 분리해, 앞으로 다른 가변 크기
  저장 방식(예: H.264 GOP 조각)을 추가할 때도 같은 실수를 반복하지 않도록 API 자체에
  경계를 명시했다(`memory_bytes()`의 docstring에 "균일 크기 가정"을 명시).
- 실험 방법론 버그(단발 timing 측정의 노이즈)를 발견한 즉시 `TIMING_REPEATS=5` 평균
  측정으로 스크립트를 고쳐 재현 가능하게 만들었다 — 앞으로 CPU 시간 측정이 필요한
  실험은 기본적으로 warm-up + 복수 회 반복 평균을 원칙으로 삼는다.
- Config 관리: JPEG quality(85 권장값)를 코드에 흩어두지 않고 실험 Config로 명시했다
  (`experiments/EXP-021/experiment.md` Configuration 참고) — 다음 세션에서 Tier별
  quality 차등 적용(Next Action) 시 이 Config를 확장하면 된다.
- 남은 한계는 숨기지 않고 Next Action(EXP-021)에 이월: Tier별 quality 차등 미검증,
  실제 카지노 유사 복잡 텍스처에서의 재검증 미실시, 멀티 채널 동시 처리 시 코어당
  채널 수 제약(≈8채널/코어) 미검증.
