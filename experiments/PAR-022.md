# PAR-022 FC-012 "구간 단위 신뢰도 표시" 가설의 반증 - Frame 노출/Cast 신호는 거꾸로 작동했다

관련 실험: EXP-025(PAR-016), EXP-026(PAR-017), EXP-027(PAR-018), EXP-028(PAR-019),
EXP-030(PAR-021), EXP-031

## 1. 한줄 요약
EXP-030이 FC-012(검정 옷 색상 오분류)의 다음 후보로 제안한 "pixel을 고치는 대신
구간 단위로 낮은 신뢰도를 표시하자"는 설계를, Frame 전체의 노출(밝기)/Cast(채널
편차) 신호로 구현해 coco128 n=21 벤치마크로 검증했더니, 신뢰도를 "high"로 표시한
구간의 Accuracy(11.5~22.3%)가 오히려 "low"로 표시한 구간(30.6~31.9%)보다 낮게
나와 가설이 정반대로 반증됐고, production에 연결하지 않기로 했다.

## 2. 문제가 뭐였는가?
EXP-026(White Balance)/EXP-028(Segmentation Mask)/EXP-030(Gamma Correction,
self/background)까지 네 가지 pixel-level 보정이 모두 FC-012를 부분적으로만
고쳤다. EXP-030은 다음 방향으로 "pixel을 고치려 하지 말고, 색상을 신뢰할 수 없는
구간 자체를 표시하자"를 제안했다. 이 실험(EXP-031)에서 그 신호를 Frame 전체
밝기(crop이 아니라 crop+배경을 포함한 전체 이미지 평균 V)로 설계해 구현했는데,
검증 결과 "밝기가 정상 범위를 벗어난 구간 = 낮은 신뢰도"라는 전제 자체가 이
classifier(method b)의 실제 측정 결과와 맞지 않았다 - 오히려 "정상 범위"로 표시한
구간의 Accuracy가 더 낮았다.

## 3. 왜 이 문제가 중요했는가?
VMS가 "이 사람은 검정 옷을 입었다"고 검색 결과에 보여줄 때, 그 판단이 신뢰할 수
있는지 아닌지를 함께 보여주는 것은 틀린 색상을 보여주는 것보다 낫다 - 카지노처럼
한 화면 안에 스포트라이트/슬롯머신 LED/역광이 섞인 환경에서는 "이 Track의 Attribute는
낮은 신뢰도 구간에서만 관측됐다"는 플래그가 사람(관제 요원)이 최종 판단을 내리는 데
실제로 도움이 될 수 있었다. 하지만 이번 실험은 그 반대 결과를 보여줬다 - 설계
의도와 반대로 작동하는 신뢰도 플래그는 플래그가 없는 것보다 더 위험하다(관제
요원이 "high confidence"로 표시된, 실제로는 더 부정확한 결과를 더 신뢰하게
만들기 때문이다). 검증 없이 이런 기능을 먼저 만들었다면 이 역효과를 발견하지
못한 채 production에 반영될 뻔했다 - "그럴듯한 설계 아이디어"와 "실제로 작동하는
기능"을 구분하는 이 프로젝트의 핵심 원칙(검증 없는 기능을 먼저 만들지 않는다,
EXP-027과 동일)이 이번에도 실제 문제를 막아낸 사례다.

## 4. 원인이 뭐였는가?
`results/EXP-031/summary.json`의 실측 데이터와 EXP-030이 이미 측정해 둔 조건별
Accuracy(`results/EXP-030/summary.json`의 `accuracy_by_condition`)를 교차로 확인해
원인을 찾았다. Alt B(Dataset 기반 Threshold) 기준 unflagged(고신뢰) 72셀의 조건별
구성을 직접 세어 보니 normal 15, **low_light 0**, strong_light 2, warm_cast 9,
cool_cast 10이었다 - 노출 신호가 low_light를 100% Flag해 unflagged에서 완전히
빠졌다. 그런데 EXP-030이 측정한 method b의 조건별 Accuracy는 low_light가
40.5%로 **가장 높은** 조건이었고, unflagged에 많이 남은 normal(33.3%)/
warm_cast(16.7%)/cool_cast(19.0%)는 오히려 더 낮은 조건들이었다. 즉 노출 신호가
"이 classifier가 가장 잘 맞히는 조건"을 가장 강하게 Flag하고, "가장 못 맞히는
조건들"을 그대로 통과시켜 unflagged subset의 Accuracy를 끌어내렸다 - 로그/코드
분석에 근거한 확인이며, 추측이 아니다. Alt C(Cast 편차 추가)가 상황을 더 악화시킨
원인도 직접 측정했다: normal 조건 자체의 Cast 편차 분포(mean=0.1719, std=0.1382)가
cool_cast(mean=0.2064)와 거의 겹쳐(EXP-027이 이미 crop 단위에서 확인한 "achromatic/
chromatic 신호가 분리되지 않는다"는 패턴을 Frame 단위에서도 반복), Cast 신호가
추가로 Flag하는 대상이 거의 무작위에 가까웠다.

## 5. A를 고민하였는데 왜 안 했는가?
Alt A(고정 휴리스틱 Threshold, V<85/V>170 - 이 Dataset을 보지 않고 흔히 쓰는 값)는
구현이 가장 단순하고 Dataset 의존적인 보정 없이 바로 쓸 수 있다는 장점이 있었다.
하지만 측정 결과(unflagged Accuracy 22.3% < Baseline 26.2% < flagged Accuracy
30.6%) Alt B(Dataset 기반)와 동일한 방향(반대)으로 반증됐고, 오히려 Alt B보다 반증
정도가 덜 심했을 뿐(Alt A 22.3% vs Alt B 15.3%) 근본적인 가설 자체가 깨졌으므로
Threshold를 더 정교하게 다듬는 것(Alt A → Alt B로의 보정)은 의미가 없었다 - 어느
Threshold를 골라도 "낮은 신뢰도로 표시한 구간이 실제로는 더 정확하다"는 반대
방향 자체는 바뀌지 않았다.

## 6. B를 고민하였고 왜 적용했는가?
Alt B(Dataset 기반 Threshold)와 Alt C(Cast 신호 결합)를 "적용"한 것이 아니라,
둘 다 가설을 보강하는 방향으로 실제 구현·측정했다는 의미에서 "B/C를 고민했다" -
Alt C는 Alt B가 못 겨냥하는 FC-012의 또 다른 축(채널 Cast)을 커버하면 가설이
성립할 수 있다는 기대로 추가했지만, 결과는 반대 방향으로 더 심해졌다(flagged_rate가
46.7%→65.7%→75.2%로 커질수록 unflagged Accuracy가 22.3%→15.3%→11.5%로 계속
나빠짐). 결국 A/B/C 중 어느 것도 채택하지 않고 전부 기각했다 - 이 PAR의 핵심은
"B를 선택했다"가 아니라 "세 변형 모두 같은 방향으로 반증됐으므로 신호 자체를
재설계해야 한다"는 결론이다.

## 7. 어떤 방식으로 검증했는가?
EXP-025/027/028/030과 완전히 동일한 Dataset(coco128 실제 COCO train2017 n=21
person crop, 수동 Ground Truth)과 완전히 동일한 5종 합성 조명(normal/low_light/
strong_light/warm_cast/cool_cast, `apply_lighting()`)을 재사용해 Before/After
비교가 유효하도록 했다(지침 37). Baseline은 EXP-030이 이미 측정한 method b 수치
(Overall 26.19%, GT=black 39.09%)를 코드 변경 없이 재실행해 동일함을 먼저 확인한
뒤, Frame 전체 밝기/Cast 편차를 GT 21개가 가리키는 고유 원본 이미지 17장에서
측정해 Alt A(고정)/Alt B(Dataset 기반 P10/P90)/Alt C(B+Cast P90) 세 Threshold
세트의 flagged_rate와 unflagged/flagged subset Accuracy를 비교했다
(`scripts/run_exp031_attribute_confidence_flag.py`,
`results/EXP-031/{predictions.csv,summary.json}`). Regression Test로
`tests/test_attribute_color.py`에 새 함수(`frame_mean_brightness`,
`classify_exposure_level`, `frame_channel_cast_deviation`) 단위 테스트 11개,
`tests/test_track_exposure_accumulator.py`에 `TrackExposureAccumulator` 누적
메커니즘 단위 테스트 7개(독립 Track 분리, 다수결 분기, forget_track 리셋 포함)를
신규 추가했다. 전체 `pytest tests/ -q`로 233 passed/7 skipped(기존 215
passed에서 신규 18개만 추가, 기존 테스트 전부 무수정 통과 - 회귀 없음)를 확인했다.

## 8. 개선된 수치적인 결과가 무엇이었는가?
이번 실험은 "개선"이 아니라 가설의 반증이 결과다 - 숫자를 그대로 기록한다
(지침 38, 성과를 위해 숫자를 조작하거나 실패 결과를 숨기지 않는다).

| Threshold 세트 (coco128 n=21×5 lighting=210셀) | Flagged Rate | Unflagged Accuracy | Flagged Accuracy |
|---|---|---|---|
| Baseline(플래그 없음, 전부 신뢰) | - | - | 26.2% |
| Alt A(고정 85/170) | 46.7% | 22.3% (Baseline보다 **낮음**) | 30.6% |
| Alt B(Dataset 기반 P10/P90) | 65.7% | 15.3% (Baseline보다 **낮음**) | 31.9% |
| Alt C(노출+Cast 결합) | 75.2% | 11.5% (Baseline보다 **낮음**) | 31.0% |

세 변형 모두 "신뢰도 high로 표시한 구간"이 "신뢰도 low로 표시한 구간"보다 덜
정확했다 - 신뢰도 표시가 설계 의도와 반대 방향으로 작동함을 확인했다.

## 9. 재발 방지 대책
- `src/attributes/color.py`의 `frame_mean_brightness`/`frame_channel_cast_deviation`
  docstring에 이번 반증 결과(구체적 수치)를 명시해, 다음 세션이 "아직 안 해본
  신뢰도 신호"로 같은 접근을 다시 시도하지 않도록 했다.
- `src/attributes/confidence.py`의 `TrackExposureAccumulator` docstring에
  "production 파이프라인에 연결하지 않음"을 명시적으로 기록하고, 이유(검증되지
  않은 신호를 신뢰도로 노출하는 역효과)를 남겼다 - 메커니즘 자체(Unit Test 7개)는
  재사용 가능하도록 유지하되, 실제 신뢰도 판단에는 쓰지 않는다는 경계를 코드
  수준에서 명확히 했다.
- `tests/test_attribute_color.py`/`tests/test_track_exposure_accumulator.py`를
  Regression Test로 추가해, 나중에 이 함수들을 다른 목적(예: 배경 기반 Gamma
  추정의 입력값 검증)으로 재사용하다가 계산 자체가 깨지는 회귀가 생기면 바로
  잡아낸다.
- FC-012(Notion 05. Failure Cases)에 confidence 신호 후보가 이제 achromatic
  채도/BGR std(EXP-027)에 이어 Frame 노출/Cast(EXP-031)까지 두 가지 모두
  반증됐음을 추가하고, Next Action을 "더 복잡한 보정/신호를 추가하기 전에 먼저
  오분류 110개 GT=black 셀을 조건×Hue bin 단위로 직접 Error Analysis할 것"으로
  전환해, 다음 세션이 같은 "그럴듯한 가설 → 반증" 패턴을 일곱 번째로 반복하기
  전에 먼저 이 결론을 읽도록 Roadmap에 남겼다.
