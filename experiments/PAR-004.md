# PAR-004 Long Running Test로 BestShot 후보 무제한 누적 Memory Leak 발견 및 Incremental Best-Tracking으로 수정

관련 실험: EXP-008, EXP-010

## 1. 한줄 요약
Long Running Test에서 파이프라인을 30분 이상 연속 실행해보니 Track마다 모든 관측 프레임의 crop 이미지를
계속 쌓아두던 BestShot 로직이 초당 약 9MB씩 Memory를 누적시키는 것을 발견했고, 프레임마다 즉시 점수를
계산해 "지금까지 최고 점수 후보 1개"만 유지하는 Incremental Best-Tracking으로 바꿔 32분 연속 실행에서도
Memory 증가가 사실상 0에 수렴함을 실측으로 확인했다.

## 2. 문제가 뭐였는가?
`run_full_pipeline.py`(EXP-008)는 각 Track이 관측될 때마다 crop 이미지를 `bestshot_candidates[track_id]`
리스트에 계속 append하고, 영상 처리가 모두 끝난 뒤 한 번에 정렬해서 최고 점수 프레임을 골라 저장했다.
EXP-008에서는 800프레임(약 33초)짜리 짧은 벤치마크만 돌려서 문제가 드러나지 않았지만, 지침 28(장시간
안정성 테스트)에 따라 EXP-010에서 같은 로직을 몇 분 이상 연속 실행해보니 RSS Memory가 349초 만에
567.9MB → 3725.4MB(+3157.5MB)까지 선형으로 치솟았고, 안전 중단 임계값(+3072MB)에 걸려 자동 종료되었다.
FPS도 25.1 → 22.0(−12.4%)으로 계속 떨어졌다.

## 3. 왜 이 문제가 중요했는가?
카지노 CCTV는 24시간 연속 가동되며, 딜러/캐셔처럼 한 자리에 몇 시간씩 머무는 대상이 항상 존재한다.
이런 대상의 Track이 오래 유지될수록 해당 Track의 crop 버퍼가 끝없이 쌓여 Memory가 늘어나고, 다중
채널(수백 대 카메라)을 한 프로세스에서 처리하는 실제 NVR/VMS 환경이라면 몇 시간 내로 OOM에 도달해
전체 영상분석 프로세스가 죽을 수 있다. 이는 BestShot 기능 하나의 문제가 아니라 시스템 전체(Metadata
Pipeline, Event Analytics, VMS Search)의 가용성을 무너뜨리는 연쇄 장애로 이어진다:
**BestShot 버퍼 무한 누적 → Memory 고갈 → 프로세스 강제 종료 → 진행 중이던 모든 Track/Event 유실 →
Forensic 검색(VMS Search)에서 해당 시간대 데이터 자체가 존재하지 않게 됨.**
FC-004(Track 소실 시 EXIT 이벤트 유실)를 고친 `forget_track()` 개선이 ROI/Line/Loitering 상태에는
적용됐지만 BestShot 버퍼에는 적용되지 않았다는 점에서, "부분적으로만 정리되는 상태 관리"가 실제로
어떻게 새로운 장애를 낳는지 보여주는 사례이기도 하다.

## 4. 원인이 뭐였는가?
`scripts/run_full_pipeline.py`(EXP-008 원본) 코드를 직접 확인한 결과, `bestshot_candidates: dict[int,
list[dict]]`에 프레임마다 `{"frame_idx", "bbox", "conf", "crop", "others"}`를 append만 하고, 이 dict
자체는 Track이 `forget_track()`으로 상태 정리될 때도 전혀 건드리지 않았다(영상 전체가 끝난 뒤 단 한
번만 순회). EXP-010에서 이 로직을 그대로 두고 200프레임 간격으로 실제 버퍼에 쌓인 관측치 개수
(`buffered_observations`)를 함께 측정했더니 프레임 수에 정확히 비례해서 증가하는 것을 확인했다
(200프레임: 797개 → 4200프레임: 16887개) — 로그/Metric으로 원인을 직접 특정했다.

## 5. A를 고민하였는데 왜 안 했는가?
Track별 관측 리스트를 최근 N개(예: 30개) 또는 상위 K개 점수만 유지하도록 자르는 "Capped Window" 방식을
검토했다. 메모리 사용량을 줄일 수는 있으나 (1) N을 얼마로 잡을지 근거가 없어 임의적이고, (2) 여전히
Track 수 × N만큼 메모리를 계속 쓰며, (3) 매 프레임 정렬·자르기 로직이 추가로 필요해 코드 복잡도가
늘어난다. 무엇보다 (4) 어차피 `bestshot_score()`를 프레임마다 즉시 계산할 수 있는데, 원본 crop 여러 개를
나중에 다시 채점하려고 계속 들고 있을 이유가 없다고 판단해 채택하지 않았다(정확도·Latency·복잡도·
메모리·유지보수성 어느 기준으로 봐도 B보다 우위가 없음).

## 6. B를 고민하였고 왜 적용했는가?
매 프레임 즉시 `bestshot_score()`를 계산하고, "지금까지의 최고 점수 후보 1개"만 유지하며 나머지는 즉시
버리는 Incremental Best-Tracking(`src/bestshot/tracker.py::BestShotTracker`)을 적용했다. Track 하나당
메모리 사용량이 관측 프레임 수와 무관하게 O(1)로 고정되고, `forget_track()` 시 dict에서 해당 항목
자체를 제거해 "지금까지 몇 명이 스쳐 지나갔는지"와도 무관하게 메모리가 유지된다. 실시간 스트림을
무한정 버퍼링할 수 없는 실제 Edge Camera/NVR 환경의 제약과도 구조적으로 더 맞아 A보다 우위라고 판단했다.

## 7. 어떤 방식으로 검증했는가?
- Dataset: `ultralytics/assets/bus.jpg`(실제 사람 4~5명) + 합성 Pan/밝기 Jitter (Wikimedia 원본 영상은
  이번 세션의 네트워크 egress 정책상 접근 불가해 대체 사용 — EXP-010 experiment.md Decision 참고)
- Configuration: YOLO11n, ByteTrack, conf=0.4, imgsz=640 (기존 실험과 동일), 동일 컨테이너/동일 하드웨어
- Baseline: 수정 전 `bestshot_candidates` 전체 누적 방식, 200프레임 간격으로 RSS/FPS/P95/버퍼 크기 측정,
  안전 중단(+3072MB) 도달 시까지 실행
- 비교 방식: 동일 스크립트(`run_exp010_long_running_test.py --mode baseline|fixed`)에서 BestShot 로직만
  교체해 그 외 조건(입력, 모델, Tracker, 측정 간격)을 완전히 통제
- Regression Test: 기존 pytest 48건 + 신규 `tests/test_bestshot_tracker.py` 5건 = 총 53건 통과 확인.
  `run_full_pipeline.py`에도 동일한 fix를 통합해 EXP-008과 동일한 저장 스키마(Track/Event/BestShot)를
  유지하도록 함(원본 영상 재확보 후 수치 재검증은 Next Action으로 명시).

## 8. 개선된 수치적인 결과가 무엇이었는가?

| Metric | Before (Baseline) | After (Fixed) |
|---|---|---|
| 연속 실행 가능 시간 | 349초(4,201 프레임)에서 안전 중단 | 1,928.8초(15,000 프레임) 정상 완료, 중단 없음 |
| Memory 증가율 | ≈ 9.0 MB/초 (선형 지속 증가) | 초기 워밍업 이후 사실상 0 (평탄) |
| RSS 총 증가량(측정 구간) | +3,157.5 MB (349초) | +258.1 MB, 이 중 대부분은 첫 14초 워밍업, 이후 14,600프레임(약 1,914초) 동안 +6MB에 불과 |
| BestShot 버퍼 크기 (프레임 4,200 vs 14,800 기준) | 16,887개 (계속 증가) | 4~5개 (활성 Track 수로 고정, 증가 없음) |
| FPS 추세 | 25.1 → 22.0 (−12.4%, 지속 하락) | 25.1 → 23.4 (±변동, 뚜렷한 하락 추세 없음) |
| 예외 발생 | 0건 | 0건 |

## 9. 재발 방지 대책
- `tests/test_bestshot_tracker.py`에 "1,000번 관측해도 버퍼 크기는 1(Track 1개당)"을 명시적으로 검증하는
  회귀 테스트를 추가해, 향후 누군가 다시 리스트 누적 방식으로 되돌리는 실수를 pytest 단계에서 즉시 잡는다.
- `run_exp010_long_running_test.py`를 재사용 가능한 Long Running Test 표준 스크립트로 유지한다(안전 중단
  임계값 포함) — 앞으로 새로운 상태 관리 로직(예: Person Re-ID Embedding 캐시, People Counting 이력)을
  추가할 때마다 동일 스크립트로 10분 이상 재실행해 유사한 무제한 누적 패턴이 없는지 확인한다.
- FC-004(PAR-002)에서처럼 "일부 상태만 `forget_track()`으로 정리되고 다른 상태는 누락되는" 패턴이
  반복되지 않도록, 새 Track 관련 상태를 추가할 때는 반드시 forget 경로에도 대응하는 정리 로직을
  같은 PR/커밋에서 함께 추가하는 것을 체크리스트로 남긴다(08. Technical Decisions에 원칙으로 기록).
- 이번 세션에서 원본 Wikimedia 영상에 의존하지 않고도 실제 사진 기반으로 재현 가능한 Long Running Test를
  구성했으므로, 앞으로 데이터셋 접근이 막힌 환경에서도 동일한 방식으로 회귀 검증이 가능하다.
