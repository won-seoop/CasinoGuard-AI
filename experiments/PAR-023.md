# PAR-023 FC-012 재검토 네 번째 라운드 - "조명 보정"이 아니라 "오분류 자체"를 직접 진단해 방향을 바꿈

관련 실험: EXP-026(PAR-017), EXP-027(PAR-018), EXP-028(PAR-019), EXP-030(PAR-021),
EXP-031(PAR-022), EXP-032

## 1. 한줄 요약
FC-012(검정 옷 오분류)를 겨냥한 조명 보정 4종 + confidence 신호 2종이 모두 실패한
이유를, 오분류 셀을 Hue 다수결 중간값(필터 폴백 여부/예측 색 분포/margin) 단위로 직접
진단해 찾아냈다 - 오분류의 다수(조명 무변형 상태에서도 40%+, 필터 폴백 경로 35~40%,
확신에 찬 오분류 80%)가 애초에 조명 보정으로는 닿지 않는 범위였고, 추가로 GT 라벨
오류 2건(1.8%)도 발견해 교정 후 재측정까지 완료했다.

## 2. 문제가 뭐였는가?
EXP-026/028/030/031 네 번의 세션에 걸쳐 White Balance, Segmentation Mask, Gamma
Correction(두 변형), Frame 노출/Cast 기반 confidence 표시를 순서대로 시도했지만 전부
FC-012(검정 옷이 strong_light/cool_cast에서 blue로 오분류)를 부분적으로만 개선하거나
완전히 반증됐다(EXP-031 Decision). 매번 "조명이 문제일 것이다"라는 가설에서 출발해
실측으로 반증되는 패턴이 반복됐고, EXP-031 Next Action은 "더 많은 신호/보정을
추가하기 전에 오분류 자체를 직접 진단할 것"을 명시적으로 요구했다.

## 3. 왜 이 문제가 중요했는가?
카지노 VMS에서 Attribute(상/하의 색상)는 "특정 옷을 입은 사람을 검색"하는 핵심
기능이다. 검정 옷은 카지노 직원 유니폼이나 정장(VIP 라운지)에서 흔한 색상이라 FC-012의
실패가 바로 이 검색 기능의 신뢰도를 깎는다. 하지만 지난 4번의 보정 시도가 매번
"그럴듯한 가설 -> 구현 -> 실측 반증"을 반복한 것 자체가 더 큰 문제였다 - 원인을 모른
채 대증 요법(조명 보정)만 계속 시도하면 production에 반영할 수 있는 해법에 영원히
도달하지 못한다. 프로젝트 전체 원칙(지침 3)이 요구하는 "문제 측정 -> 원인 분석 ->
해결 비교" 순서를 Attribute 색상 분류 영역에서 처음으로 제대로 지킨 사례다.

## 4. 원인이 뭐였는가?
`src/attributes/color.py`의 `region_dominant_color()`(Hue 다수결 로직) 내부 동작을
그대로 유지한 채, 중간값(필터 통과 비율, 폴백 발동 여부, 1/2위 Hue bin 득표, 최종
HSV)을 반환하는 진단 버전(`region_dominant_color_diagnostic` 등, EXP-032)을 추가해
coco128 GT=black 110셀 전수를 직접 조사했다. 로그/Metric 기반 확인 결과:
- GT=black 오분류의 예측 색상은 blue가 29.9%(b)/44.9%(c_wb)뿐이고 나머지는
  orange/red/gray 등으로 분산됐다 - FC-012의 "검정→blue" 프레이밍이 실패 양상을
  절반도 설명하지 못했다.
- 조명을 전혀 가하지 않은 normal 조건에서도 45.45%(b)/40.91%(c_wb)가 오분류됐다 -
  조명 보정이 손댈 수 있는 범위 밖의 오류가 이미 절반에 가깝다.
- 오분류의 40.3%(b)/34.7%(c_wb)가 `min_filtered_fraction` 폴백 경로(필터 통과 픽셀
  <30% -> 원본 전체 픽셀로 복귀)에서 발생했다 - PAR-016이 "진짜 검정이 필터에 다
  걸리는 문제"를 막으려 넣은 안전장치 자체가 배경/피부색 재유입으로 새 오분류 경로가
  됐다.
- 오분류의 약 80%(narrow_margin_fraction 19.4%/20.4%의 여집합)는 Hue 다수결
  1위/2위 득표 차이가 커서(확신에 찬 오답), threshold 미세조정으로는 거의 못 고친다.
- normal 조건 오분류 10건을 crop 이미지로 직접 육안 재확인한 결과 2건(`000000000086_0`
  upper, `000000000634_0` upper)은 classifier가 아니라 **GT 라벨 자체의 오류**였다
  (흑백/그레이스케일 원본 사진에서 실제로는 밝은 셔츠인데 "어두운 자켓"으로 잘못
  라벨링됨).

## 5. A를 고민하였는데 왜 안 했는가?
**A: 다섯 번째 조명 보정/신호를 추가로 설계한다**(예: 더 정교한 Hue 경계값 조정,
또 다른 confidence 신호). 장점은 기존 네 번의 실험과 동일한 패턴이라 구현이 빠르고
비교군이 이미 갖춰져 있다는 것이다. 하지만 이번 진단으로 조명 무관 오류가 전체의
40%+·확신에 찬 오답이 80%라는 것이 드러난 상태에서, 가설도 세우지 않고 다섯 번째
보정을 또 시도하면 EXP-031이 이미 경고한 "그럴듯한 가설에서 출발해 반증되는" 패턴을
반복할 위험이 컸다. 근거 없이 다음 시도를 선택하는 것 자체가 이 프로젝트의 핵심
원칙(지침 3, 55: 가설을 먼저 기록하고 검증)을 어기는 것이라 채택하지 않았다.

## 6. B를 고민하였고 왜 적용했는가?
**B(채택): 새 보정을 만들지 않고, 기존 로직의 중간값을 직접 계측하는 진단 함수를
추가해 오분류 자체를 구조적으로 분석한다.** EXP-031 Next Action이 정확히 이 방향을
요구했고, "무엇을 고쳐야 할지 모른 채 또 고치는" 것보다 "무엇이 실제로 틀리게
만드는지 먼저 확인"하는 것이 근거 있는 다음 행동을 고를 수 있게 한다. 기존 공개
함수(`region_dominant_color`, `classify_person_attributes_with_mask*`)는 건드리지
않고 진단 변형만 별도로 추가해(thin wrapper 리팩터링으로 동작 비변경을 Regression
Test로 고정) production 코드에 대한 Risk 없이 분석할 수 있었다는 점도 B를 선택한
이유다.

## 7. 어떤 방식으로 검증했는가?
EXP-027/028/030/031과 완전히 동일한 Dataset(coco128 n=21 person crop GT, 5종
합성 조명)·Detector(yolo11n.pt conf=0.4)·Segmenter(yolo11n-seg.pt, IoU 매칭)로
GT key 21개가 그대로 재현됨을 재확인했다. GT=black 110셀(22 base × 5 조건)에 대해
method "b"와 production이 실제로 쓰는 "c_wb"(EXP-029/PAR-020) 양쪽을 진단
함수로 전수 조사했고, 결과를 `results/EXP-032/{error_rows.csv,
error_rows_gt_corrected.csv, summary.json}`로 저장했다. GT 라벨 오류 2건은
`results/EXP-032/crops/*.jpg`를 직접 Read 도구로 육안 확인해 확정했고, 교정 전/후
두 GT 세트로 같은 파이프라인을 다시 돌려 비교했다(과거 PAR-017/018/019/021/022의
원본 기록은 당시 GT 기준으로 보존, 변경하지 않음). 진단 함수 9개 신규 Unit Test를
추가해 `region_dominant_color`/`classify_person_attributes_with_mask*`의 기존 동작이
리팩터링 후에도 바뀌지 않았음을 Regression Test로 고정했다(`pytest tests/ -q`:
242 passed/7 skipped, 기존 233에서 신규 9개만 추가, 회귀 없음).

## 8. 개선된 수치적인 결과가 무엇이었는가?
이 실험은 "classifier를 고치는" PAR이 아니라 "왜 못 고쳤는지 진단하는" PAR이라
Accuracy 개선 수치는 없다(production 코드 변경 없음, 지침 8대로 숫자를 지어내지
않는다). 대신 두 가지 정량 결과를 남긴다:

| Metric | 수치 |
|---|---|
| method b 오분류 중 "blue"로 틀린 비율(FC-012 표적) | 29.9%(20/67) |
| c_wb 오분류 중 "blue"로 틀린 비율 | 44.9%(22/49) |
| method b normal(조명 무변형) 조건 오분류율 | 45.45%(10/22) |
| c_wb normal 조건 오분류율 | 40.91%(9/22) |
| method b 오분류 중 필터 폴백 경로 비율 | 40.3%(27/67) |
| c_wb 오분류 중 필터 폴백 경로 비율 | 34.7%(17/49) |
| 오분류 중 Hue 다수결 margin이 좁은(<0.6) 비율 | 19.4%(b)/20.4%(c_wb) |

GT 라벨 교정(2/110셀, 1.8%) 전/후 비교:

| Metric | Before(원본 GT) | After(2셀 교정) |
|---|---|---|
| method b 전체 Accuracy | 39.09% | 42.00% |
| method b normal Accuracy | 54.55% | 60.00% |
| c_wb 전체 Accuracy | 55.45% | 60.00% |
| c_wb normal Accuracy | 59.09% | 65.00% |

## 9. 재발 방지 대책
- `region_dominant_color_diagnostic()` 등 진단 함수는 `src/attributes/color.py`에
  영구 보존한다(Unit Test 9개로 Regression 고정) - 다음에 또 다른 보정을 시도할 때
  "실제로 무엇이 바뀌었는가"를 다시 이 진단 함수로 확인할 수 있다.
- GT 라벨 오류가 과거 4개 PAR(017/018/019/021/022)에 영향을 줬는지 확인하기 위해
  `results/EXP-032/`에 원본/교정 두 버전의 전체 측정치를 모두 남겼다 - 상대적 순위
  (baseline<a<b<b_wb, Mask+WB 결합이 최고 등)는 바뀌지 않아 과거 PAR의 결론 자체는
  유효함을 확인했다(절대 수치만 소폭 이동).
- 다음 세션은 가설 없이 다섯 번째 보정을 만들지 않고, 이번에 특정한 "필터 폴백 경로
  재설계"(오분류의 35~40%를 차지)부터 착수하도록 EXP-032 Next Action과 Notion
  Roadmap에 구체적으로 남겼다 - "무엇을 먼저 고쳐야 하는가"에 대한 근거 없는 선택을
  막기 위함이다.
- GT 라벨 품질 문제(21개 crop 재사용·4번 재검증 없이 재활용)를 메타 교훈으로 기록:
  작은 n의 평가 Dataset은 라벨 오류 1건이 미치는 영향(0.9pp/셀)이 크므로, 다음에
  Dataset을 확장하거나 재사용할 때는 전체 GT를 주기적으로 재검증하는 절차가 필요하다
  (21개 crop × 42개 영역 전체 재검증은 Next Action으로 이월).
