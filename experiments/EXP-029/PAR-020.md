# PAR-020 Attribute Metadata를 실시간 파이프라인에 연결할 때 호출 빈도 설계

관련 실험: EXP-025(PAR-016), EXP-026(PAR-017), EXP-027(PAR-018), EXP-028(PAR-019), EXP-029

## 1. 한줄 요약
Attribute 색상 분류(c_wb)를 매 프레임 호출하면(대안 A) 실시간 파이프라인 FPS가 59% 떨어짐을
구현 전 실측으로 먼저 확인하고, BestShot 확정 시점에 Track당 1회만 호출하는 방식(대안 B)으로
`run_full_pipeline.py`에 실제로 연결해 FPS 저하를 0.28%로 줄였다.

## 2. 문제가 뭐였는가?
EXP-025~028은 Attribute(상/하의 색상) 분류의 Accuracy만 오프라인 정지 이미지(coco128 crop)
로 측정했고, 실제 Detection+Tracking+BestShot이 매 프레임 실행되는 실시간 파이프라인에
연결했을 때 전체 처리 속도에 얼마나 영향을 주는지는 한 번도 측정하지 않았다. 지침 12/19는
"BestShot 확정 시점" 또는 "Track마다"라는 표현으로 호출 빈도를 암묵적으로 제한했지만, 이를
코드로 강제하거나 실측으로 검증한 적이 없어 "매 프레임 호출하는 구현을 그대로 production에
붙였다가 실시간 처리가 깨지는" 위험이 구현 시점까지 그대로 남아 있었다.

## 3. 왜 이 문제가 중요했는가?
카지노 CCTV는 다채널(수백~수천 채널)을 동시에 실시간으로 처리해야 한다. Attribute(상/하의
색상)처럼 "검색 편의 기능"에 가까운 모듈이 Segmentation 모델 추론이라는 무거운 연산을 매
프레임마다 반복하면, Detection/Tracking/Event(Intrusion·Loitering 등)처럼 보안상 핵심적인
기능의 실시간성(EXP-008이 확인한 FPS 27.7)이 함께 깎여나간다. 연쇄 영향: Attribute 설계
실수 → 전체 파이프라인 FPS 저하 → Event 탐지 지연(Intrusion/Line Crossing의 실시간 대응
능력 저하) → VMS가 "지금 일어나는 일"을 늦게 보여줌. 즉 부가 기능 하나의 설계 실수가 핵심
보안 기능의 실시간성까지 깎아먹을 수 있다는 것이 이 문제의 핵심이다.

## 4. 원인이 뭐였는가?
`scripts/run_exp029_attribute_pipeline_integration.py`로 동일 900프레임·동일 시나리오에서
Attribute 호출 빈도만 다른 두 variant를 실측 비교했다: 매 프레임 호출(대안 A)은 활성 Track
수(평균 4~5명, bus.jpg에 보행자 여러 명 포함)만큼 Segmentation 추론(평균 54.8ms/호출)이
누적돼 총 2045회 호출이 발생했고, 파이프라인 전체 P50 Latency가 73.2ms→267.8ms로 그 비용만큼
그대로 늘어나 FPS가 10.68→4.38(−59%)로 떨어졌다. Track당 1회(대안 B)는 같은 조건에서 호출이
16회로 줄어(전체 Detection 호출의 1.8%) FPS 저하가 0.28%에 불과했다 - 원인은 단순히 "무거운
연산을 얼마나 자주 반복하느냐"였고, 로그/latency_breakdown.csv로 직접 확인했다(추측이 아님).

## 5. A를 고민하였는데 왜 안 했는가?
**대안 A: 매 프레임, 활성 Track마다 Attribute를 다시 계산.** 장점은 구현이 단순하고(BestShot이
아직 확정되지 않은 시점에도 "지금까지 최선"의 Attribute를 즉시 보여줄 수 있어) 중간 상태
조회에 유리하다는 것이다. 하지만 실측 결과 FPS가 59% 떨어져(10.68→4.38) 지침 24(Edge
Optimization)가 명시한 핵심 Trade-off(Accuracy vs Latency vs Model Size)를 명백히
위반했고, 애초에 Attribute는 검색 편의를 위한 부가 Metadata(지침 19 "Attribute Classification
자체가 프로젝트 중심이 되어서는 안 된다")이므로 핵심 실시간 처리 능력을 이 정도로 희생할
이유가 없었다. 다채널 환경에서는 채널 수만큼 이 저하가 곱해지므로 더 치명적이다.

## 6. B를 고민하였고 왜 적용했는가?
**대안 B: BestShot이 확정되는 시점(Track 소실/영상 종료)에만 Track당 정확히 1회 호출.**
BestShot 자체도 "Track마다 대표 프레임 1장"이라는 같은 철학으로 설계돼 있어(지침 12,
PAR-004의 Incremental Best-Tracking과 동일한 방향) Attribute를 거기에 맞춰 1회로 제한하는
것이 설계상 자연스러웠다. 실측으로도 FPS 저하가 0.28%에 불과해 실시간 처리 능력을 거의
희생하지 않으면서 Track마다 Attribute Metadata를 여전히 얻을 수 있었다 - "중간 상태를 실시간
조회할 수 없다"는 대안 A 대비 유일한 단점은, 애초에 Attribute가 VMS 검색(사후 조회)을 위한
Metadata(지침 16/17)라는 목적과 상충하지 않는다.

## 7. 어떤 방식으로 검증했는가?
- Dataset: egress 정책상 crowded_intersection_1080p.webm 접근 불가(재확인)로 ultralytics
  내장 bus.jpg + Pan 합성 시나리오(EXP-010/017/023과 동일 패턴) 사용. 사람 등장/소멸을
  3회 반복(ByteTrack track_buffer 30프레임보다 긴 110~130프레임 간격)해 Track이 실행
  전체에 걸쳐 여러 번 생성·소멸하도록 구성.
- Configuration: YOLO11n(conf=0.4, imgsz=640)+ByteTrack, yolo11n-seg.pt(EXP-028과 동일
  Segmenter), 900프레임, variant={none, per_frame, per_track}.
- Metric: FPS, 프레임당 Latency(P50/P95/P99), Attribute 호출 횟수, 호출당 평균 Latency.
- Baseline: variant="none"(Attribute 없음)을 같은 스크립트·같은 시나리오로 함께 측정해 세
  variant를 동일 조건에서 직접 비교(EXP-008의 원본 영상 기준 수치와는 섞지 않음).
- Regression Test: `pytest tests/ -q`로 전체 Unit Test 재실행(202 passed, 7 skipped - 기존
  197 passed에서 신규 5개만 추가, 기존 테스트 전부 유지). `MetadataStore.update_attributes()`
  신규 메서드, `classify_track_attributes_once()`(mask_provider 주입 가능한 순수 함수)에
  대한 Unit Test를 새로 작성.

## 8. 개선된 수치적인 결과가 무엇이었는가?

| Metric | Baseline(none) | 대안 A(per_frame) | 대안 B(per_track, 채택) |
|---|---|---|---|
| FPS | 10.68 | 4.38 (-59.0%) | 10.65 (-0.28%) |
| P50 Latency | 73.2ms | 267.8ms | 72.7ms |
| P95 Latency | 96.9ms | 358.8ms | 99.6ms |
| Attribute 호출 수(900프레임) | 0 | 2045 | 16 |

## 9. 재발 방지 대책
- `run_full_pipeline.py`에 Attribute 호출을 실제로 연결할 때 대안 B(Track당 1회, BestShot
  확정 지점 2곳: 중간 소실 시 / 영상 종료 시)만 구현하고, 대안 A(매 프레임)는 코드에도
  추가하지 않았다 - 나중에 "실시간 미리보기"가 필요해 대안 A를 다시 검토하더라도 이 실험의
  실측 수치(-59% FPS)를 먼저 참고하도록 experiment.md에 명시했다.
- `MetadataStore.update_attributes()`와 `classify_track_attributes_once()`에 대한 Unit
  Test를 추가해, 향후 Attribute 저장 로직이나 mask_provider 주입 방식이 바뀌어도 회귀를
  바로 잡아낼 수 있게 했다.
- "Segmentation 모델을 무거운 연산으로 보고 호출 빈도를 설계 단계에서부터 제한한다"는 이번
  결정을 08. Technical Decisions에 기록해, 향후 다른 모델(Re-ID Embedding 등)을 Track/BestShot
  파이프라인에 추가할 때도 "몇 프레임마다/몇 Track마다 호출할 것인가"를 구현 전에 먼저
  실측하는 절차를 재사용할 수 있게 한다.
- `attribute_calls` 카운터와 실제 저장된 Track 행 수가 어긋나는 현상(ByteTrack 내부
  track_buffer와 파이프라인의 10프레임 Timeout 불일치)을 Failure Case로 남기지는 않았지만
  Next Action에 명시해, 다음 Tracking 관련 세션에서 재조사하도록 이어둔다.
